pi-harness redesign

The 11-page synthesis put Apache Hamilton — a static DAG of pure functions — as insight-kit's spine. But the real workload, an analyst agent doing exploratory analysis, is agentic: the graph emerges from tool-use decisions at runtime, it is not fixed beforehand. This page redesigns insight-kit ground-up as a pi extension — a harness that registers claim-emission tools and lifecycle hooks. A 7-member council reshaped the first draft: not "durable agents as the spine" but a three-layer split — freeze the gate, not the generator.

3 layers durable agents generate → claim gate · frozen → pure compute · pinned → provenance

§0Why reframe — agentic loop, not static DAG

A Hamilton DAG is fully determined before runtime. An analyst loop is not — the analyst reads a .pq file, forms a hypothesis, pulls another, revises. The graph emerges. Force exploratory analysis into a static DAG and analysts do one of two things: over-engineer the DAG upfront, or route around it with side effects — and side effects break provenance anyway.

M-1 · graph timing
DAG fixed at import; analyst graph is decided turn-by-turn. The two never line up — every exploration becomes a DAG rewrite.
M-2 · hooks are a side-door
Claims ride Hamilton lifecycle hooks. The claim — the actual product — is a bolt-on to a compute framework that does not know what a claim is.
M-3 · no agent surface
Hamilton has nodes, not tools. An LLM agent calls tools. The seam needs a tool layer Hamilton does not provide.
M-4 · runtime ≠ product
insight-kit's deliverable is a validated claim with provenance — a contract. Coupling that contract to one compute library is an abstraction error.

There is already a working proof of the alternative. The audit-engine pi extension — built in a sibling project (email-ops-as-a-service) — runs claim-emission plus maker/checker review in exactly this shape: emit_finding ≈ claim, manifest.jsonl ≈ provenance trace, run_check ≈ validators, the verdict cascade ≈ critic tier. It exists and it runs.

honest caveat — what the PoC does and does not prove
The audit-engine used stateless subprocesses (pi -p spawned per role), not durable agents. It proves claim-emission works on pi's tool model. It proves nothing about durable, heartbeat-driven agents. The council flagged this directly — citing the PoC as evidence for a durable-agent design is equivocation. This page keeps the distinction load-bearing: see §6.

§1pi in 60 seconds

pi (@mariozechner/pi-coding-agent) is a model-agnostic coding-agent runtime. It ships the loop, not an opinion. You bring the model, the tools, and the system prompt; pi runs the standard agentic tool-use cycle and persists the conversation.

The composition seam is one factory call. The host supplies cwd, model, system prompt, tool definitions; pi discovers extensions and assembles the session:

// the seam — host builds the session, extensions ride along
import { createAgentSession, discoverAndLoadExtensions } from "@mariozechner/pi-coding-agent";

const extensions = await discoverAndLoadExtensions([".pi/extensions"]);  // → insight-kit loads here
const session = await createAgentSession({
  model:       provider.resolve("claude-opus-4-7"),
  customTools: extensions.tools,        // ik_claim_emit, ik_run_check, ...
  systemPrompt: roleSystemPrompt,       // analyst | critic | conductor
});
await session.prompt(goalSpec);             // the loop runs until the agent stops

§2The three-layer architecture

The first draft of this redesign made durable, self-improving heartbeat agents the orchestration spine. The council rejected that 7‑0 — but the Round‑2 steelman rescued the useful core and produced a sharper design. The pivotal cut, four members reaching it independently: freeze the gate, not the generator.

the conflation the council caught
"Git is non-deterministic; its commits are still auditable." The draft conflated the producer must be reproducible with the product must be reproducible — two different claims. Provenance does not require a deterministic analyst. It requires a deterministic gate and a deterministic compute. The analyst above the gate may drift, learn, and explore freely — because nothing downstream trusts its output until it crosses the gate.

That yields three layers, each with its own determinism contract and its own runtime:

Layer 3 · orchestration loop  —  pi
The analyst / critic agentic loop. A pi extension registers the claim tools + provenance hooks. May be stateful, adaptive, durable. Need not be deterministic.
runtime: pi · determinism: not required · §5
▼   the only thing that crosses: a schema-valid claim   ▼
Layer 1 · claim gate / contract  —  runtime-agnostic
Schema + content-addressed provenance + critic verdict. The real insight-kit. One tool — ik_claim_emit — is the sole way a claim enters. Must be deterministic, immutable, replayable.
runtime: none — pure library · determinism: mandatory · §3
▼   the gate calls compute to derive + fingerprint   ▼
Layer 2 · compute spine  —  Hamilton or plain functions
Pure functions, explicit lineage, pinned per run. Hamilton's discipline survives even if the library is swapped out. This is the only layer where the Hamilton-vs-pi question is still live — and it is a swappable driver choice.
runtime: Hamilton / functions · determinism: mandatory · §4

§3Layer 1 · the claim gate

The gate is the real insight-kit — and it depends on neither Hamilton nor pi. One tool is the sole entry point for a claim. The schema validates at the gate; a rejection throws and forces the agent to re-emit with corrected fields. This is the audit-engine's emit_finding pattern, renamed and made the spine.

// the gate — one tool, schema-validated, the sole way a claim enters
export const ikClaimEmit: ToolDefinition = {
  name: "ik_claim_emit",
  parameters: ClaimSchema,                 // Typebox — also the Layer-A validator
  execute(input) {
    const claim = validateClaim(input);     // throws → agent must re-emit
    claim.data_fingerprint = contentAddress(claim.inputs);  // sha256 of inputs
    claim.claim_fingerprint = contentAddress(claim);        // addresses the claim itself
    getRun().append(claim);            // → claims.jsonl, immutable line
    return { claim_id: claim.id, fingerprint: claim.claim_fingerprint };
  },
};

Three insight-kit validation layers map onto the gate cleanly:

insight-kit layerWhere it runsWhat it checks
Layer A · schemaThe gate — synchronous, at emitShape, types, required fields. Rejection forces re-emit.
Layer B · uniquenessagent_end hook — post-runClaim-ID uniqueness, supersedes-chain integrity.
Layer C · cross-claimagent_end hook — post-runCross-claim invariants (annual = Σ monthly), critic verdict join.

What "auditable" means — mixed by tier

The council's pivotal unresolved question: does auditable require bit-deterministic replay of the claim, or only of the gate decision? Resolved mixed by tier — the audit standard rises with the stakes:

TierAudit standardWhat must be replayableGenerator freedom
published · board / founder / sharedbit-deterministic replayRe-running must re-derive the identical number + chart. Agent version, code version, data fingerprint all pinned.Durable generator must snapshot; the gate re-derives independently.
draft · internal / exploratorygate-decision + traceThe accept/reject, the inputs, and the critic reasoning trace. The number itself need not bit-match.Durable, self-improving generators run free.

§4Layer 2 · the compute spine

Below the gate sits pure computation: functions with explicit inputs, no hidden state, content-addressed outputs. Hamilton expresses this well — but the gate depends on the discipline (pure functions, explicit lineage), not the library. Plain typed functions satisfy the same contract.

# compute spine — pure, pinned, fingerprinted. Hamilton OR plain functions.
def mer_monthly_by_channel(orders_pq: pl.LazyFrame, spend_pq: pl.LazyFrame) -> pl.DataFrame:
    # pure: same .pq inputs → same frame, every run. no I/O side effects.
    return (orders_pq.join(spend_pq, on="month")
              .with_columns((pl.col("revenue") / pl.col("spend")).alias("mer"))
              .collect())

# the gate fingerprints every input before calling compute:
#   data_fingerprint = sha256(orders.parquet) + sha256(spend.parquet)
#   code_fingerprint = sha256(source of every function on the path)
# published tier: all fingerprints frozen in run.json → bit-replay possible
why the published tier needs a pinned spine
Bit-deterministic replay (published tier, §3) is only possible if Layer 2 is frozen per run: the data fingerprint, the code fingerprint, and the model/agent version all recorded in run.json. Replay = re-run the pinned compute against the pinned data. The durable analyst above the gate can have evolved since — it does not matter, because replay never touches Layer 3. That is the whole point of freezing the gate, not the generator.

This is the one layer where the Hamilton-vs-pi question stays open — and it is small. Hamilton buys you a DAG visualiser, @check_output, the cache adapter, and the h_dlt/h_polars plugin ecosystem. Plain functions buy you zero dependencies. Either satisfies the gate's contract. Treat it as a swappable driver — §9.

§5Layer 3 · the pi extension

insight-kit ships as one pi extension. Its index.ts default export receives the ExtensionAPI and registers three things: the claim tools, the RunState factory, and the provenance hooks. The structure is lifted directly from the audit-engine PoC.

// index.ts — the insight-kit extension entry
export default function insightKit(pi: ExtensionAPI): void {
  // 1. tools — the analyst's surface (the gate, §3)
  pi.registerTool(ikClaimEmit);      pi.registerTool(ikRunCheck);
  pi.registerTool(ikFeatureGet);     pi.registerTool(ikClaimLink);
  pi.registerTool(ikCritiqueEmit);

  // 2. determinism — pin temperature for published-tier runs
  pi.on("before_provider_request", (r) => { if (run.tier === "published") r.temperature = 0; });

  // 3. provenance hooks — passive, never break the run
  pi.on("tool_call",    (e) => getRunOrNull()?.manifest(e));   // → manifest.jsonl
  pi.on("tool_result",  (e) => getRunOrNull()?.manifest(e));
  pi.on("agent_end",        () => finalizeRun());          // → claims.jsonl + run.json
  pi.on("session_shutdown", () => finalizeRun());          // dual path for pi -p
}
ToolRoleWhat it does
ik_claim_emitanalystThe gate. Sole way a claim enters. Schema-validated, fingerprinted, appended to claims.jsonl.
ik_run_checkanalyst / criticRuns a validator script (uv run --no-project) — Layer B/C checks, hypothesis tests. Output capped, appended to manifest.
ik_feature_getanalystResolves a catalog feature by name — kills inline-math hallucination. Misses route to a feature request.
ik_claim_linkanalystDeclares a claim's input claims — supersedes / baseline / intervention edges.
ik_critique_emitcriticAttaches a refutation to a claim — the critiques[] array, surfaced as a non-ignorable rail flag.

RunState — accumulate, finalize once

A mutable accumulator opens at run start, closes once. getRun() throws when no run is active (tools — strict); getRunOrNull() returns null silently (hooks — passive, so a telemetry miss never kills a healthy run). finalizeRun() is idempotent via a completedAt guard — the agent_end + session_shutdown dual path can both fire and write once.

interface RunState {
  run_id: string;  tier: "published" | "draft";
  claims: Claim[];          rejectionCount: number;   // schema rejections — a quality signal
  fingerprints: { data: string; code: string; agent: string };
  completedAt?: string;     // idempotency guard — finalize writes once
}

§6Durable agents — in their correct place

The council did not ban durable agents. It relocated them. A durable, heartbeat-driven, self-improving agent is the wrong thing to put on the provenance path — but the right thing to put above the gate, as the claim generator.

above the gate · OK to drift

Durable analyst generator

heartbeatper-agent memorymailbox

Long-lived. Accumulates context across sessions, refines hypotheses, remembers a goal's quirks. Free to be non-deterministic — nothing trusts its output until ik_claim_emit.

the boundary

The frozen gate

ik_claim_emitschema + fingerprint

The only thing that crosses is a schema-valid, content-addressed claim. Deterministic. Immutable once written. The generator's drift stops here.

below the gate · must not drift

Pinned compute + provenance

pure functionspinned per run

Deterministic, fingerprinted, replayable. Hamilton's discipline. A durable agent never writes here.

Self-improvement — only as append-only claim events

A durable agent that rewrites its own behaviour is fine if each mutation is itself an immutable, content-addressed claim event, and the agent version is pinned per run. Then a published-tier claim records exactly which agent vN produced it — the improvement is logged, not hidden. Self-improvement becomes a tracked product feature, not silent infrastructure drift.

Taleb · the barbell
90% deterministic, replayable core — the gate and the pinned compute. 10% aggressive — the durable generator as a swappable, experimental front-end. Never the half-durable middle: a platform that is partly audited and partly self-modifying. The generator's mutations are themselves immutable claim events, so the durable agent gets antifragile — it gains from each failed analysis — without destroying replayability.
the hard rule
A durable, self-improving agent may generate claims and explore data. It may never be the gate, own the compute, or write provenance directly. "You cannot audit a moving auditor" — but you can audit what a moving auditor hands across a frozen gate.

§7Skills + Evidence binding

Two surfaces ride the same extension: the skills that shape the analyst's context, and the Evidence binding that consumes the claims.

Skills — context-engineering units

pi discovers skills/ the same way it discovers extensions ("pi": { "skills": [...] }). insight-kit ships analyst skills as markdown context units — the pattern from Agent-Skills for Context Engineering: frontmatter (name, description), When-to-Activate, Core, Gotchas, References; under 500 lines; progressive disclosure — metadata loads, full body activates on trigger.

SkillTeaches the analyst
extract-from-pqHow to pull data from .pq files via h_polars without re-deriving aggregations inline.
write-a-claimThe claim schema, the fmt hints, code-first then narrative — how to satisfy the gate on the first emit.
critic-checklistRefutation recipes — cherry-picked baselines, partial-month windows, sign flips.

Context engineering is the discipline here: curate the smallest high-signal token set. Skills activate on trigger, they do not all load — attention is the budget.

Evidence binding — claims out

claims.jsonl is the seam to the reporting site. Evidence.dev consumes it: the <ClaimNum> component resolves claim_id + field at build, hard-errors on a missing claim — a literal number can no longer exist in board prose. Charts render from V-tier claim specs; the spec is rendered to PNG (vl-convert) so the vision-critic can see the chart and check it against claim.fields.

§9Council · the deliberation that reshaped this

7 members · 2 rounds · blind analysis then cross-examination with a mandatory steelman. The steelman is what rescued durable agents — it surfaced the gate/generator split.

Ada · formal systems

Hamilton and pi sit at different layers; the synthesis conflated compute with coordination. Self-improvement breaks the reproducibility invariant — exclude mutable agents from the provenance boundary. A boundary condition, not a blanket ban.

Feynman · first principles

Provenance needs a replayable record; a self-improving agent rewrites its own record — "that's not provenance, that's forensics." Use pi's ExtensionAPI for tools and hooks. Keep the compute spine stateless. Run the damn thing.

Torvalds · shipping

Don't rewrite a working library because the framework is shiny. pi as a thin emission/validation adapter. Self-improvement is a product feature, not infrastructure — ship it separately or not at all.

Meadows · systems

The load-bearing structure is the error-correction loop. A durable agent introduces uncontrolled write paths to the claim stock. Layered architecture: deterministic compute core, pi orchestration above, schema-validated immutable claim event as the interface.

Taleb · tail risk

The claim record is Mediocristan — bounded. A self-improving agent loop is Extremistan — unbounded drift, and it rewrites the record that would let you detect the drift. Barbell: deterministic core + swappable pi front-end, never the half-durable middle.

Machiavelli · power

The PoC already exists — a revealed preference; watch that the deliberation doesn't just ratify it. Don't defer. Force the criterion: if run-reproducibility is contractual, the durable-agent path is disqualified at that tier.

Socrates · assumptions

Reject the binary. The core is a runtime-agnostic claim contract — schema, content-addressed provenance, deterministic gate. Freeze the gate, not the generator: "Git is non-deterministic; its commits are still auditable." Seven members nearly conflated producer with product.

Synthesis · verdict

7‑0 against durable agents on the provenance path — but not a blanket ban. The reshape: a three-layer split. Layer 1 — a runtime-agnostic, deterministic claim gate (the real insight-kit). Layer 2 — pure, pinned compute; Hamilton-vs-pi is a swappable driver here, and only here. Layer 3 — pi as the agentic loop; durable agents permitted as claim generators upstream of the frozen gate, self-improvement only as append-only claim events, version pinned per run. The "auditable" standard rises by tier. "Side-by-side, defer the choice" survives only for the driver layer — deferring the core contract would be a cop-out.

§10pi-harness vs Hamilton — side by side

The earlier decision was "present both side-by-side, defer the choice." The council narrowed where that is legitimate. Deferring the core contract is a cop-out — so the gate is decided: runtime-agnostic, §3. Deferring the compute driver is sound optionality — so that one stays a genuine side-by-side.

the seam — they compose, they do not compete
The two are not rivals once the three-layer split is accepted. Layer 3 is pi — the agentic analyst loop. Layer 1 is neither — a runtime-agnostic library. Layer 2 is the side-by-side: Hamilton when you want the DAG visualiser, @check_output, the cache adapter and h_dlt/h_polars plugins; plain typed functions when you want zero dependencies. Both satisfy the gate's contract. The decision can be made per goal, even per claim — and deferred honestly, because it is a driver swap, not an architecture.
Verdict · council-reviewed · 2026-05-21

Rebuild insight-kit as a three-layer pi harness — freeze the gate, not the generator.

  1. Layer 1 · claim gate. Runtime-agnostic library. ik_claim_emit is the sole entry; schema-validated, content-addressed, immutable. This is the real insight-kit — decided, not deferred.
  2. Layer 2 · compute spine. Pure functions, pinned per run, fingerprinted. Hamilton or plain functions — a swappable driver, the one honest side-by-side.
  3. Layer 3 · orchestration loop. A pi extension. Registers the claim tools + passive provenance hooks. May be stateful and adaptive.
  4. Durable agents. Permitted as claim generators upstream of the frozen gate — never the gate, never the compute, never writing provenance. Self-improvement only as append-only claim events; agent version pinned per run.
  5. Audit standard. Mixed by tier — published demands bit-deterministic replay; draft demands gate-decision + reasoning trace.
  6. Honesty. The audit-engine PoC validated stateless subprocesses, not durable agents. Phase 1 builds the gate + a stateless loop first; durable generators are a later, opt-in phase.

Glossary

pi
@mariozechner/pi-coding-agent — a model-agnostic coding-agent runtime. Ships the tool-use loop + an ExtensionAPI; brings no model opinion of its own.
Harness
A pi extension — a file that receives the ExtensionAPI and registers tools, lifecycle hooks, and provider hooks into every session. insight-kit ships as one.
Claim gate
Layer 1. The single tool (ik_claim_emit) through which a claim enters. Schema-validated, content-addressed, immutable. Deterministic — "freeze the gate, not the generator."
Claim generator
A durable analyst agent above the gate. May drift, learn, self-improve — nothing trusts its output until it crosses the gate.
RunState
The mutable run accumulator — claims, fingerprints, rejection count. Opens at run start, finalized once via a completedAt idempotency guard.
Lifecycle hook
A pi callback — tool_call, agent_end, session_shutdown, etc. insight-kit's hooks are passive (getRunOrNull) so a telemetry miss never kills a run.
manifest.jsonl
Append-only trace of every tool call + result. The full audit replay; claims.jsonl is the clean validated output beside it.
Content-addressed
An artifact keyed by the sha256 of its own bytes. A claim's data_fingerprint + claim_fingerprint make it self-verifying and replayable.
Mixed-by-tier audit
Published tier = bit-deterministic replay of the claim. Draft tier = gate-decision + reasoning trace only. The standard rises with the stakes.
Durable agent
A long-lived agent with a heartbeat, mailbox and per-agent memory. Permitted here only as a generator upstream of the gate.
audit-engine PoC
A working pi extension in email-ops-as-a-service — claim-emission + maker/checker review. Used stateless subprocesses; validates the tool model, not durable agents.
Context engineering
Curating the smallest high-signal token set within the model's attention budget. Skills are markdown context units with frontmatter + progressive disclosure.

A 7-member multi-persona deliberation that pressure-tested this design on 2026-05-21 — §9.
