Should insight-kit sit on top of Apache Hamilton?

insight-kit is a provenance + claim-emission library for analyst loops: Run() context manager, structured claim tiers, Layer A/B/C validation, runs/ dir on disk. The pattern visible in dockblocks-ops/.insight-kit (48 runs, Apr–May 2026) is a hand-sequenced exploratory loop with heavy boilerplate. Hamilton is a DAG framework with native lifecycle hooks, tags, materialisers, caching, and a notebook→prod story. A prior memory already records the decision to build consumer-repo v2 on Hamilton — this artifact is the architecture-level how, what to keep, what to drop, what's the lift.

script + Run()→ Hamilton @node + @tag→ InsightKitHook→ Run / Claim / Manifest→ parquet + DuckDB→ Evidence.dev
baseline claim→ execute intervention (Meta API / Shopify)→ checkpoint date→ delta + critic claim
Jump to intervention loop ↓ Jump to verdict ↓

§1What insight-kit is, in one breath

A library that wraps analyst Python scripts in a with Run(topic, agent) context and emits typed, ID-namespaced claims (DOCK-D-001, NMK-BA-002) plus content-addressed artifacts (parquet + sha + schema) into a per-run directory. Three validation layers (A real-time, B post-run, C cross-project) enforce schema, namespace, referential integrity, edge rules, external caveats. A pre-existing Hamilton adapter (src/insight_kit/hamilton/adapter.py) already implements an InsightKitHook that listens to post_node_execute and routes nodes tagged emit="metric|critique|viz" or claim_tier=... into Run.emit_* / Run.claim().

Important — already partially landed
insight-kit already ships a Hamilton lifecycle hook at src/insight_kit/hamilton/adapter.py:67. The question is no longer should we adopt Hamilton? — it is how aggressively, and what manual code do we now retire?

Today's iteration shape (from dockblocks-ops/.insight-kit/runs/)

  • 48 runs in 11 days. Bootstrap cluster (8 runs × 16 min), deep-dive cluster (10 runs at 09:09–09:10), dedup-hygiene loop (4 sequential runs, one failed, three rewrites).
  • Each run = its own script.py + manifest.json + claims.jsonl + output/{metrics,derived,viz}/*.parquet. Sequencing is manual; cross-run lineage exists only via the input_claims back-references in each claim.
  • Council pattern: a single megabatch run (2026-05-05-brevo-attribution/, 38 files) bundles 12 persona scripts (munger, meadows, rams, socrates, kahneman) and produces 5 derived + 5 critic claims by re-reading the same input parquet five times in five separate processes.
The smell
Three iteration anti-patterns repeat across the 48 runs: (a) N councils re-reading the same input, (b) dedup re-runs as parameter sweeps that should be one parameterised node, (c) claim-emission tightly coupled to compute, so editing claim text re-runs the compute. Hamilton fixes all three structurally.

§3.5Going deeper — claims as tagged nodes

§3 above is the conservative refactor: Hamilton runs the compute, insight-kit's Claim / Run / Manifest objects stay as Python data classes, the hook bridges the two. A more ambitious option is on the table: collapse insight-kit's parallel object model into Hamilton tags. A claim becomes a node with @tag(claim_tier=…, claim_id=…). A run becomes Driver.execute() itself. The manifest becomes a ResultBuilder adapter that serializes the execution trace. Layer A/B becomes GraphValidator / NodeValidator adapters that run at driver-build time.

Why this is on the table now
Hamilton's @tag system + dr.what_is_upstream_of() + node.tags filter recapitulates almost every primitive insight-kit defines today as a separate Python object. The examples/lineage/ idiom — @tag(source="prod.titantic", owner="data-engineering", importance="production") on the data-loader node — is exactly the shape insight-kit's InputRecord dataclass tries to express in Python.

Two paths, side-by-side

default · 4 dev days

Conservative — Hamilton as runner

insight-kit keeps Claim, Run, Manifest, Goals, Layers A/B/C, agents.yaml, claims_registry.yaml, Evidence seam. Hamilton owns the compute graph + lifecycle. The InsightKitHook bridges them. Per-run procedural script.py is replaced by one declarative module per analysis topic. Cherry-pick @tag, @parameterize, @subdag, @check_output, cache adapter, materialisers. This is §3 above.

Pilot: rewrite 2026-05-05-brevo-attribution as one Hamilton module — 38 files collapse to ≤2.

opt-in · ~2 weeks

Deep refactor — claims AS tagged nodes

Collapse insight-kit's parallel object model. Claim, Run, Manifest, Goals, Layers, agent taxonomy, supports/refutes, supersedes — all expressed as Hamilton tags + adapters. Lineage query = dr.what_is_upstream_of(). Cache invalidation = claim invalidation. dr.visualize_execution() doubles as the manifest visualization. What's left in insight-kit: CLI (ik run/validate/bootstrap/preflight), DSL conventions, the adapters themselves, runs/ directory layout, Evidence seam, skills, personas. Net ~40% smaller library.

Pilot: only after conservative ships. Run on one analysis at a time. Hamilton tolerates a mix.

What survives in insight-kit after the deep refactor

  • The CLI — ik run, ik validate, ik bootstrap, ik preflight.
  • The DSL conventions — what tags mean, claim-ID regex, namespace.
  • The adapters themselves — InsightKitGraphValidator, InsightKitResultBuilder, InsightKitCriticEdgeRule.
  • The runs/ directory layout — written by the result-builder adapter, not a context manager.
  • The Evidence.dev page generator + DuckDB view bridge.
  • The skills/ — citation-hygiene, eval-protocol, schema-drift, etc.
  • The personas — council voices, prompts, model dispatch.

Net effect: roughly all of provenance/ and most of validation/ collapse into adapters; everything that's about analyst workflow semantics (skills, personas, goals lifecycle, Evidence seam) stays.

Trade-offs

pro

Why you'd want it

  • Single source of truth for graph + provenance (no parallel object models).
  • dr.visualize_execution() is also the manifest visualization.
  • Cache invalidation = claim invalidation. Edit a node → only its downstream claims re-emit.
  • Hamilton-native tooling (Hamilton UI, OpenLineage, MLflow) lights up "for free" if needed later.
  • Less custom Python, more conventions → smaller maintenance burden.
con

What it costs

  • More upfront work (~2 weeks vs 4 days for conservative).
  • Steeper learning curve — new analysts must learn Hamilton tag conventions.
  • Hamilton's reactive lifecycle (post-node-execute) doesn't model pre-compute concerns elegantly (goal declaration, prompt versioning) — those still need separate state.
  • Tighter coupling to Hamilton's evolution; Apache project, but still incubating.
  • Tag soup risk: a node with 8 tags is hard to grok at a glance.
Recommendation
Default to conservative; opt into the deep refactor topic-by-topic. Pilot the deep refactor on one analysis (brevo-attribution again) only after the conservative pilot succeeds. Each module can pick its level — Hamilton tolerates both. A repo can hold conservative modules and deep-refactor modules side by side; the on-disk .insight-kit/runs/<id>/ contract is identical from Evidence.dev's perspective.

What does not belong in Hamilton

  • Goal lifecycle (open_queue.jsonl, closed.jsonl, catalog.yaml). It's a CLI-driven hypothesis ledger; trying to model goal state as Hamilton config is an anti-pattern.
  • Annotations (kahneman/socrates auto-emit). These ride on top of a closed run's claims; not a node-time event. Keep as a separate post-hoc job.
  • Layer C cross-project validation. It scans many runs across the filesystem; runs outside any single Driver. Keep as a CLI (ik validate).
  • Council persona dispatch (which LLM, which prompt). That's prompt orchestration; Hamilton nodes call into it but don't model it.

§5.5The intervention loop — the real pilot

Pivot. The integration's value isn't a faster council megabatch. It's a closed-loop intervention engine. The pattern is already half-built in your-business/consumer-repo/data/initiatives_log.jsonl — every record is an intervention (G4-2026-05-04, F7-2026-05-05, DIAG-DISMISS-2026-05-05) that was executed (Meta Marketing API POST, customer-file hash + upload, Events-Manager kebab-click) and is now waiting for a checkpoint date to be re-measured.

Why Hamilton turns this from a JSONL register into a system

Right now initiatives_log.jsonl is hand-edited: someone runs the intervention, hand-writes the baseline, and remembers to come back on the checkpoint date. The post-metric column stays null until a human triggers the re-measure. The intervention itself (API POST, audience upload) lives in ad-hoc scripts under data/agent_runs/.... Three failure modes follow: (a) baselines drift before they're locked, (b) checkpoints get missed, (c) the re-measure code differs from the baseline code, so the delta isn't apples-to-apples.

With Hamilton modeling the loop, an intervention is a DAG: the baseline node, the action node, and the checkpoint node share upstream functions and config. Same code computes baseline and post — only the data window changes. The cache + fingerprint guarantees the comparison is honest.

T0 · execute

What that means concretely

  • One module per lever. your-business/consumer-repo/interventions/g4_exclusion.py holds: baseline fn, execute fn, post fn, delta fn, critic fn. All five share upstream meta_insights(adset_ids, window).
  • Side effects are first-class nodes. The Meta API POST is a Hamilton node tagged @tag(side_effect="meta_api", idempotency_key=…). The hook records the request + response into the run dir. A second execute() with the same idempotency key cache-hits and refuses to re-POST.
  • Checkpoint = second Driver run, same module. ik checkpoint <initiative_id> calls Driver.execute([compute_post_cpa, measure_intervention, critic_intervention_verdict]) with window="14d_post". The cache holds the baseline; only post + delta + critic compute.
  • initiatives_log.jsonl becomes a materializer output, not a hand-edited file. A custom InitiativeLogSaver appends one record per execute, updates the same record on checkpoint.
  • Re-measurement is automatic and replayable. Anyone can run ik checkpoint G4-2026-05-04 --as-of 2026-06-19 30 days later and get a longer-window post-metric; the baseline doesn't move because its cache entry is content-addressed.
Why this is the pilot that actually proves the point
Brevo-attribution would prove "Hamilton collapses 38 files to 2". Useful, but it's a refactor. The intervention loop proves insight-kit + Hamilton is a closed-loop ops system for founder-greenlit actions (CAPI fix, exclusion wiring, audience refresh, spend ramp), not just an analysis kit. The four pending records in initiatives_log.jsonl become the test cases.

Glossary · this page

Dotted terms link here.
Run
Context manager (with Run(topic, agent)) that opens a timestamped run directory, captures git SHA + env.lock, and closes by writing manifest.json + checksums.sha256.
Claim
A typed, ID-namespaced assertion (DOCK-D-001) with a ClaimTier, optional confidence score, supports/refutes edges, and supersedes chain. Emitted by Run.claim() or the Hamilton hook.
ClaimTier
Enum defining the domain taxonomy: raw, derived, critic, initiative, viz, counterfactual, etl_*. Enforced by Layer A validation.
manifest.json
Per-run summary file written by Run.__exit__. Contains inputs, outputs, git SHA, env lock reference, timing, and a list of claim IDs emitted during the run.
Layer A/B/C
Three validation tiers: A = real-time (schema, namespace regex, claim-ID format); B = post-run (cross-run uniqueness, referential integrity); C = cross-project (external-caveat rules, Layer C scanner run via ik validate).
@tag
Hamilton decorator that attaches arbitrary key-value metadata to a node. insight-kit reads emit, claim_tier, claim_id, side_effect, idempotency_key tags to route node outputs into claim emission.
post_node_execute
Hamilton lifecycle hook fired after each node completes. The InsightKitHook lives here: it reads the node's tags and dispatches to Run.emit_* / Run.claim().
InsightKitHook
Hamilton NodeExecutionHook at src/insight_kit/hamilton/adapter.py:67. Bridges Hamilton lifecycle events to insight-kit's Run/Claim API. Fires on post_node_execute for tagged nodes only.
HamiltonCacheAdapter
Hamilton adapter that computes a fingerprint (code hash + input data hash + config) per node and skips recomputation when the fingerprint matches a prior run. Collapses parameter-sweep re-run loops.
@parameterize
Hamilton decorator that fans one function into N sibling nodes, each with a different parameter binding. Used to replace the council megabatch pattern (5 persona scripts → 1 parameterized node).
@subdag
Hamilton decorator that embeds a reusable sub-graph into a parent graph, optionally with config overrides. Used to model "critic of X across 5 angles" as a one-liner instead of 5 scripts.
@check_output
Hamilton decorator attaching schema or range validators to a node's output. Validation failures fire the hook → insight-kit emits a critic-tier claim recording the failure.
@save_to.parquet
Hamilton materializer that writes a node's output DataFrame to a Parquet file at a declared path. Replaces imperative Run.emit_metric() calls; the materializer owns the I/O.
initiatives_log.jsonl
JSONL register at your-business/consumer-repo/data/initiatives_log.jsonl. Each record is one founder-greenlit intervention with baseline metric, checkpoint date, and (eventually) post-metric + delta filled by a Driver run.
baseline claim
A raw-tier claim emitted at T0 of an intervention, locking the pre-action metric value. Content-addressed by the cache adapter so it cannot drift even if the measurement code is re-run later.
intervention loop
The closed-loop system modeled in §5.5: baseline node → execute (side-effect) node → checkpoint node → delta node → critic node. One Hamilton module per lever; checkpoint = second Driver run on the same module with a new data window.
side-effect node
A Hamilton node tagged @tag(side_effect=…, idempotency_key=…) that performs an external write (Meta API POST, audience upload). The hook records request + response; a duplicate execute with the same idempotency key is refused by the cache.
fingerprint
Hash of (code + inputs + config) used as the cache key by HamiltonCacheAdapter. If fingerprint matches a prior run, the node is skipped. Guarantees baseline and post-metric use identical computation.
GraphValidator
Hamilton adapter hook called at driver-build time (before any node executes). In the deep-refactor path, replaces insight-kit's Layer A validation: claim-ID regex, namespace rules, critic-edge constraints.
ResultBuilder
Hamilton adapter that serializes the execution trace after Driver.execute() completes. In the deep-refactor path, this writes manifest.json instead of Run.__exit__.
consumer-repo
The your-business/consumer-repo/ analysis package. v2 is being built on Hamilton. Contains interventions/ (per-lever Hamilton modules), data/initiatives_log.jsonl, and the Evidence.dev delta dashboard.
Evidence.dev seam
The reporting layer: Hamilton @save_to.parquet writes artifacts → build_duckdb_views.py mounts them as DuckDB views → Evidence SQL pages query those views → markdown pages render charts and claim badges.
