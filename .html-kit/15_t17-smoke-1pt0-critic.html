The T17 score jumped from 0.83 to 1.00.
That is less interesting than it looks.

6/6 structural checks 3 variables changed at once n=1 trial omp + opencode-go + deepseek-v4-flash score.py is structural, not analytical

Yesterday's run dropped its socket mid-critic and scored 0.83. Today's run finished clean and scored 1.0000. The difference looks like a triumph for the new agent / channel / model stack. It is not — at least, not yet. Three variables flipped in the same commit, one trial fired, no prior-run artifacts survived for forensic comparison. What we have evidence for is far narrower than "the new stack works better"; what we have evidence for is "a clean run finishes the file score.py was looking for." Those are different sentences. This page separates them.

§1What the smoke test actually does

Strip the celebration. The harness is a five-step Docker container that drives one autonomous agent through one canned analyst+critic loop against the Nairomarket business data, then runs a six-point structural grader on whatever the run dir contains. set -uo pipefail — no e. A failed agent is still feedback; we want the grader to see the wreckage either way. That is the test's character: it does not abort on the agent's failure, it grades the rubble.

1hostrun-eval.sh: MI client id/secret → infisical login --method=universal-auth → JWT (len=407) → infisical run --silent -- docker run -e OPENCODE_GO_API_KEY
2buildentrypoint.sh: fail-fast if OPENCODE_GO_API_KEY missing → python scripts/build_duckdb_views.py creates 11 DuckDB views from parquet (g4f7_adset_daily, g4f7_order_composition, claims_manifest, …)
3driveomp -p --no-session --no-lsp --no-skills --no-extensions --provider opencode-go --model deepseek-v4-flash --thinking off --api-key "$OPENCODE_GO_API_KEY" "$(cat deploy/eval/instruction.md)" — the analyst→critic loop runs unattended, writes into a run dir under data/agent_runs/<ts>_analyst_<goal>/
4locateRead .eval/run_dir.txt first; fall back to ls -dt data/agent_runs/*_analyst_*. If neither, exit 1: "no analyst run dir produced — omp never started the run"
5scorepython deploy/eval/score.py "${RUN_DIR}" → six PASS/FAIL lines on stderr → one float on stdout
6preservecp -r "${RUN_DIR}" .eval/run → host sees it via the new .eval-out:/app/.eval bind mount

That is the whole thing. Five lines of bash drive one container. There is no judge, no LLM-as-grader, no learned reward — by design. score.py's docstring is explicit:

"Tracer scope: structural completeness only — did the harness produce a structured, complete run? Analysis correctness is what Harbor/AutoAgent optimize later (the 10 error-class reward functions go here eventually)." — deploy/eval/score.py:5-7

Read that carefully. Structural completeness only. The grader does not read the analysis. It does not ask whether the buyer-exclusion attribution is right. It checks file existence, JSON parseability, and length thresholds. A 1.0 means the agent finished writing the files. It does not mean the agent finished thinking.

§2The six checks, decoded

Each check is a single boolean. The float is the unweighted mean. Below: what each one measures, what the prior run did, what this run did, what would silently pass.

check 1claims.jsonl has ≥1 valid claimPASS · PASS
check 2analyst claims (MD-D-*) presentPASS · PASS
check 3critic claims (MD-C-*) presentPASS · PASS
check 4findings_analyst.md non-stub (>400 B)PASS · PASS
check 5flip ↑findings_critic.md present (>200 B)FAIL · PASS
check 6queries/*.sql archivedPASS · PASS

Only one check flipped: findings_critic.md must be longer than 200 bytes. The prior run died with a socket-closed error inside the critic phase; the file existed (the analyst pre-creates it as a stub at run-dir setup) but stayed at stub length. This run wrote 12,335 bytes of critic prose. That is the entire delta.

The honest reading

The score moved because the critic phase completed. The five other checks were already passing in the failed run because the analyst phase had completed before the socket dropped, and the critic had even managed to emit MD-C-* JSONL lines into the append-only claims.jsonl before its markdown writer was cut off. Check 5 is a single-byte threshold; it is also the one most exposed to transport failure, because it is the last large write the agent does in the run.

Some of these checks are also looser than they look. Check 1 accepts any JSON-parseable line as a "valid claim", with no schema validation; an empty {} would pass. Check 2/3 only require any claim_id starting with MD-D/MD-C respectively; one claim of each tier passes the gate, regardless of completeness. Check 4's "non-stub" rule is literally "replace this stub" not in fa_text and len(fa_text) > 400 — a 401-byte markdown file that happens not to contain the stub phrase would pass. Check 5 is 200 bytes — six sentences. Check 6 is any(qdir.glob("*.sql")) — one empty .sql file passes.

That is the grader. The cliff between 0.83 and 1.00 is one socket connection that did not drop.

§3Three variables changed at once. Don't pretend otherwise.

Commit 9f5b23d swapped three independent components of the harness in a single diff. We have one trial under the new configuration. The question we cannot answer with this data is which of the three drove the improvement. We can only say "the bundle works at n=1".

There are also three additional changes that quietly moved at the same time and could have affected outcomes:

  • Flag surface widened: --no-lsp --no-skills --no-extensions --thinking off --api-key were added at the omp swap. These reduce the surface area where omp might do extra work and bail. "Thinking off" alone changes the wall-clock duration of a run by orders of magnitude on reasoning-tuned models.
  • Cred chain became MI-mediated: bare -e OPENROUTER_API_KEY → infisical login --method=universal-auth → INFISICAL_TOKEN → infisical run --silent -- docker run -e OPENCODE_GO_API_KEY. This is unrelated to model quality but adds a JWT-expiry failure mode we have not yet tripped. JWT lifetime is ~10 min; this run completed in 9m 53s. Cutting it fine.
  • Bind mount appeared: .eval-out:/app/.eval. Without it, the prior failure left zero forensic evidence on the host. We literally only know the prior failure mode from in-band log capture, not from artifacts. The asymmetry of evidence is itself a methodological problem — the new stack cannot fail in the same invisible way the old one did, because we'd see the partial artifacts now.
⚠ The causal trap

"We swapped agent+channel+model and the score went up — the new stack is better" is the kind of sentence that, said with confidence after a single trial, locks in a configuration we may not actually need. The prior failure was probably transport (socket drop is a TCP-level event). If that's right, only the channel swap (openrouter → opencode-go) was load-bearing, and we are now paying $10/mo + Bun's instrumentation tax + deepseek's verbosity profile for a problem one variable solved. We do not yet know which variable did the work.

§4What an isolation experiment would look like

If the user wanted causal evidence (not just operational reassurance), the smallest experiment that would let them disentangle the three variables is a 2×2×2 cell matrix with k=3 trials per cell. Eight cells × three trials = 24 runs. At ~10 min each that's four wall-clock hours; on opencode-go's budget it costs nothing.

# Factorial design — drop reasonably
# Factors: AGENT × CHANNEL × MODEL  (2 × 2 × 2 = 8 cells, k=3 each)

AGENT   = [pi-0.75.4,            omp-15.2.4]
CHANNEL = [openrouter,           opencode-go]
MODEL   = [claude-sonnet-4.6,    deepseek-v4-flash]

# What you learn
#   - Drop rate per CHANNEL (marginalize over AGENT, MODEL)  → channel hypothesis
#   - Mean critic.md bytes per MODEL                          → model verbosity ⇒ check 5 risk
#   - omp_exit==0 rate per AGENT                              → agent robustness
#   - Interaction: deepseek × opencode-go cell variance       → coupling effects
#   - Score variance within (omp, opencode-go, deepseek) cell → repeatability floor

Critical instrumentation the current harness does not emit and would need to:

  • Per-phase timing: how long analyst took, how long critic took, where exit happened. The current log only knows "omp exit code N".
  • Socket lifecycle events: connect, idle, close-reason. The prior failure's diagnosis ("socket dropped mid-critic") came from the agent's own stderr — it should come from tcpdump-level evidence or from explicit per-message ACK logs.
  • Critic.md byte count over time: watch -n1 wc -c findings_critic.md while the run executes would tell you whether the file grows monotonically (suggesting streaming writes) or appears at the end (suggesting buffered final write). The grader's 200-byte threshold is sensitive to which.
  • JWT remaining lifetime at exit: the run came within ~17s of the universal-auth JWT's 10-min default expiry. One slower run and the cred chain breaks for a different reason than the score reflects.

Until that instrumentation exists, every future score change has the same interpretability problem this one does.

§6Surfacing what the prior run would have lost

The clean run gives us first-time forensic access to what the critic phase produces when it finishes. This material existed conceptually before but was destroyed on container exit. Reading it now is the closest we get to understanding what the 0.83 actually cost us — not in score-space, but in signal-space.

The analyst (karpathy persona) is honest about the methodological constraint:

"Quasi-experimental constraint: There is NO clean control group. Only two adsets (MaxValue_Local_All, Local_Volume_Broad_KE) were ever spending on OUTCOME_SALES. The other 9 spending adsets in the window are non-OUTCOME_SALES and not comparable. Every claim carries this caveat. I never use RCT-causal language." — findings_analyst.md · karpathy

And the critic (taleb persona) finds the analyst's overconfident decomposition and rips through it. This is the content that would have been zero bytes if the socket had dropped 30 seconds earlier:

"The analyst reports 'CPM dropped 9.4%' using weighted CPM (340→308). This is misleading. Mean CPM increased from 360 → 372 (+3.3%). P90 CPM expanded from 481 → 587 (+22%). Max CPM jumped from 553 → 698 (+26%). The weighted CPM dropped only because the impression mix shifted to cheaper days. The right tail is worsening, not improving." — findings_critic.md · taleb · MD-C-G6-002
"IC→purchase improvement is decaying. The May 4 week shows a dramatic jump, but by May 18 both adsets are back near pre-period baseline (~8.6%). The 14d aggregate rate of 11.17% is inflated by the strong first week. If this trend continues, the H1 effect is temporary — a one-time flush of high-intent prospects, not a durable targeting improvement." — findings_critic.md · taleb · MD-C-G6-003
"H1 (buyer exclusion, 40%) and H4 (funnel CVR, 10%) are the same mechanism: the IC→purchase improvement. The analyst acknowledges overlap qualitatively but still assigns separate attribution shares (40%+10%=50% combined for what is fundamentally one mechanism). This double-counts the same observed effect." — findings_critic.md · taleb · MD-C-G6-007

The critic also rebuilds the decomposition into something defensible: H1 from 40% → 35% (decay + overlap), H3 from 20% → 10% (CPM tail), H4 → 0% (merged into H1), H6 from 8% → 12% (pre-trend), and — most importantly — residual from 15% → 36%. Over a third of the CPA improvement, the critic concludes, cannot be confidently assigned to any named hypothesis. That number is the honest one. The analyst's 15% residual was the optimism.

The asymmetry of what we score vs what we lose

The grader does not know that this critic content is good. It only checks bytes > 200. A 201-byte placebo critic would pass check 5 identically. The 12,335 bytes of substantive challenge — pre-trend contamination, distributional tail risk, H1↔H4 double-counting, IC→purch decay, invalid control comparison — exists for human readers, not the score. The score is blind to the very signal we ran the harness to produce.

§7Durable learnings

  1. A structural grader cannot tell you the analysis is correct. It tells you the agent finished. Treat 1.0 as "the pipe is clear", not "the result is right". Plan for a second-tier grader (LLM-as-judge or hand-scored rubric on the 10 error classes mentioned in score.py's docstring) before promoting any number above 1.0 to a credible claim about analytical quality.
  2. Single-trial bundle swaps are diagnostically inert. If three variables move and you do not run a factorial, you have an observation, not a finding. The two cheapest preconditions for any future big change: (a) one isolated swap at a time, or (b) k≥3 trials per cell when bundling.
  3. The last large write is the most exposed. Check 5 (findings_critic.md) failed because it sits at the tail of the critic phase. The same pattern — final-write-fails-silently — will haunt any other artifact the agent produces near the end of its trajectory. Mitigation: stream-write critic.md incrementally (header + per-claim sections as they're produced), so a mid-critic drop still leaves the threshold satisfied with degraded content. The grader will pass; a downstream LLM-judge will catch the truncation.
  4. No bind mount = no post-mortem. The 6b73452 failure left zero on-host artifacts. We only know the failure mode from in-band log capture, which is exactly the part the failing component is least able to produce reliably. The fix in 9f5b23d (.eval-out:/app/.eval) should be a permanent invariant of any containerized agent run, not a feature.
  5. JWT lifetimes are unannounced deadlines. The run completed in 9m 53s against a ~10-min universal-auth JWT. The next run that takes 11 minutes (longer critic, slower model, retry, deepseek's tail latency) will fail in the cred layer for reasons the score will mis-attribute to the agent. Either lengthen the JWT TTL explicitly or refresh mid-run.

§8Taleb mode — what could still go wrong

Tail risk · model

deepseek-v4-flash's 384K out cap is invisible until it bites

The critic.md was ~12KB. We are at <4% of the cap. A more demanding analyst prompt (council-of-five, multi-claim critic) lands us at 80%+ silently. The grader won't tell us; it'll just see a complete file.

Tail risk · stack

opencode-go is a single vendor we just made load-bearing

Subscription paused, billing dispute, IP-block, regional outage — any of these kills the harness atomically. The cred chain has no fallback to openrouter. Add one before this becomes a Friday-afternoon discovery.

Survivorship bias

We celebrate the one trial that worked

If we'd run the same omp+opencode-go+deepseek bundle ten times and seen one 1.0 + nine drops, we'd be telling a different story. We have not done that. The denominator is one. We do not know the variance.

Goodhart drift

The grader will become the target

Once we optimize against score.py (Harbor RL, reward shaping), the agent will learn to write 201-byte critic stubs and structurally-valid empty claims. The 6 checks then measure "we trained against this", not "the run was good". Plan grader hardening (semantic validity, claim-citation cross-checks, length distribution priors) before reward-shaping starts.

Forensic blind spot

We cannot replay the failed run

No prior-run artifacts survived. Every claim about why pi+openrouter dropped its socket is inferred from a one-line stderr message. We are reasoning about a known unknown with a single data point and no diff.

Cargo cult

"omp is better than pi" — based on what?

omp may genuinely be more robust under Bun. It may also be that the agent we just tested is unusually capable on the one prompt we threw at it. We have no comparative data on prompts the agent struggles with, only on the one canned analyst→critic loop that's now part of the harness.

The actual takeaway

The score moved from 0.83 to 1.00. The system did not move that much.

What we have evidence for: one socket stayed open this time, in a configuration where three things changed at once. What we do not have evidence for: that the new stack is causally better, that the analysis is correct, that the score will repeat, or that we'd see the same critic prose under a different prompt.

  1. Treat 1.0 as a pulse, not a heartbeat. Repeat the run k=3-5 times with no changes. If you see variance, the score itself has variance. If you see 5×1.0, you have a heartbeat.
  2. Run the isolation matrix. 8 cells × 3 trials = 24 runs at ~$0 incremental on opencode-go. The diagnostic value dwarfs the cost.
  3. Add per-phase timing + socket-lifecycle + JWT-remaining-TTL to the entrypoint log. The next failure is otherwise un-debuggable.
  4. Stream-write findings_critic.md. The last large write should not be a single artifact gating the score.
  5. Promote the bind mount to invariant. Any future container run without forensic capture is a regression of methodology, regardless of what the score says.
  6. Before reward-shaping against score.py, harden the grader. Add semantic checks (claim-id format regex, citation cross-validation, critic→analyst MD-C-target lookup, prose length-distribution prior) so Goodhart's law does not eat the rubric.

One-sentence verdict: the harness now produces complete runs in the configuration we tested once, and that is a useful waypoint — but the green light on 1.00 is for "the rubric is satisfied", not for "the system is understood". Both sentences fit on the same page; only one of them is true.
