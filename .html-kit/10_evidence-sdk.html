Evidence today vs Evidence SDK

reports/ today = CLI-driven, markdown + SQL, built-in components, config files. The SDK at packages/lib/sdk/ turns Evidence into a library — datasource connectors, page builders, query runners, SSR hooks, plugin contracts — that you call from your own TypeScript. Same product, very different blast radius. Two-panel below: each row is one axis; left = today, right = SDK.

authoring· data sources· page generation· components· query runtime· build pipeline· SSR / routing· theming
Today — markdown-first

With SDK — programmatic
library · TS · plugins

How a page actually gets made — agent run swimlane

The Evidence .md page is the LAST artifact in a chain of role-separated runs (see .agents/analyst · critic · renderer). Each run produces a tier of claims and writes a working artifact the next role consumes. Swimlane below mirrors the production sequence — claim IDs from 2026-04-26_*_analyst-funnel_g2-levers + sibling runs.

data-engineer (ETL) analyst (D-tier) critic (C-tier) renderer (I + V) generator-assisted

Read this: data-engineer materializes views → analyst derives D-claims + writes output/synthesis/<slug>.md → critic challenges (may force a revised analyst pass via refutes) → renderer reads BOTH the synthesis prose AND the surviving D/C claim graph to author reports/pages/<slug>.md + emit I + V claims → Evidence compiles. The SDK seam is the green dashed node: a build-dev generator slots alongside renderer to emit per-claim receipts + provenance rails, not in place of it.

01Authoring surface

Renderer authors by hand today

Renderer reads the analyst's synthesis narrative, picks a layout_type, maps claims to components, drops in chart specs, types the prose body. Every page = one human pass. Per-claim receipt pages, provenance rails, lever-receipt sidecars — all hand-written.

  • Synthesis narrative is the spine. output/synthesis/g2_levers.md from the analyst becomes the prose body — renderer edits prose, doesn't generate it.
  • Layout choice is a judgment call. 6 layout types (receipt · narrative · investigation · metric · browse · audit). Renderer picks based on which D/C/X claims are focal.
  • Claim-to-component mapping is hand-typed. <ClaimBlock claim_id="DOCK-D-004"/>, <ClaimDelta before="…" after="…"/>, <ProvenanceRail/>. One tag per claim.
  • V-tier viz specs duplicated. Every chart re-justified — V-001 says "LineChart because temporal; bar would lose seasonality". Sibling pages repeat the framing.
  • Cost: 10 lever pages → 10 hand-passes through claim mapping + provenance rail + receipt block. Drift on layout, component props, copy.
# reports/pages/levers/g1_spend_reallocation.md # ← renderer writes this whole file by hand, # pulling prose from analyst's synthesis/g1_levers.md --- title: "G1 — Spend Reallocation" layout_type: narrative # renderer judgment --- ```sql kpi select cpa_baseline, cpa_post from claims_manifest where claim_id = 'NM-G4-DELTA-001' ``` <BigValue data={kpi} value=cpa_post/> ## Why this lever # ← prose lifted/edited from analyst synthesis <ClaimBlock claim_id="NM-D-004"/> <ClaimDelta before="DOCK-D-003" after="NM-D-004"/> <ProvenanceRail focal="NM-D-004"/>

Generators take the boilerplate sdk

Renderer still writes the narrative spine + picks layout. Generator takes the per-claim repetitive parts: receipt pages (one per I-claim), provenance rails (one per focal D-claim), V-tier viz JSX from V-claim specs, indexes. Hybrid: human authors the page; build emits the sidecars.

  • Receipt pages auto-emitted. Every I-claim gets a levers/<claim_id>.md receipt page from leverTemplate(claim). 10 I-claims = 10 receipts, no hand-typing.
  • Provenance rail = generated component. Renderer drops <ProvenanceRail focal="…"/> ; the generator walks the claim graph + emits the supporting/refuting/superseding chain at build time.
  • V-claim → chart spec deterministic. V-001 emits output/viz/g1_cpa_delta.json ; generator wraps it in the right Evidence chart component. Justification text stays human (the V-claim statement).
  • Narrative pages stay human-authored. Generator does NOT write the synthesis prose, does NOT pick the layout type, does NOT choose which claim is focal. Those remain renderer judgment calls.
  • Split: reports/pages/levers/g1_spend_reallocation.md (narrative page) — still hand-typed by renderer. reports/pages/receipts/<claim_id>.md (per-claim receipt) — generated.
// reports/build-dev/generators/receipts.ts // emits ONE receipt page per I-tier claim — boilerplate only import { PageBuilder } from '@evidence-dev/sdk/build-dev'; import { getClaims, getProvenance } from '../lib/claims'; import { receiptTemplate } from '../templates/receipt'; for (const c of await getClaims({tier: 'I'})) { const prov = await getProvenance(c.claim_id); // receiptTemplate fills frontmatter + ClaimBlock + // ProvenanceRail + supersedes ladder — deterministic. PageBuilder.emit( `receipts/${c.claim_id}.md`, receiptTemplate(c, prov), ); } // reports/pages/levers/g1_spend_reallocation.md // ← still hand-authored: narrative + layout choice + focal claim // but it now LINKS to the generated /receipts/NM-G4-DELTA-001

02Data sources

Built-in connectors today

  • 14 built-ins (duckdb, postgres, csv, bigquery, …) declared in sources/*/connection.yaml.
  • insight-kit runs reach Evidence via DuckDB views built by build_duckdb_views.py.
  • Refresh = re-build the warehouse file; no source-level cache awareness.
# sources/nairomarket/connection.yaml type: duckdb options: filename: '../../data/parquet/nairomarket.duckdb'

Custom datasource plugin sdk

  • Implement DatasourcePlugin: introspect(), runQuery(), refresh hooks.
  • insight-kit-source reads .insight-kit/runs/** directly. No intermediate DuckDB rebuild.
  • Typed columns; live refresh on new run; per-claim caching.
// plugins/insight-kit-source/index.ts export const plugin: DatasourcePlugin = { type: 'insight-kit', introspect: async () => readManifests('.insight-kit/runs'), runQuery: async (sql, ctx) => ikQueryEngine(sql, ctx), };
03Page generation

None — manual today

  • No build-time page emission.
  • Templating = manual copy/paste between sibling levers.
  • viz/evidence/generators/*.ts exist but only emit JSON sidecars, not pages.

build-dev page builder sdk

  • Hook into dev/build pipeline; emit .md at build start, before source-refresh.
  • Per-intervention page renders from initiatives_log.jsonl automatically.
  • 10 founder actions → 10 pages, zero hand-editing.
  • Hot-reload on generator edit.
04Components

Built-in + local Svelte pkg today

  • Core components (BigValue, LineChart, Grid, Callout).
  • @insight-kit/viz-evidence already wired via the implicit plugin loader.
  • No typed component props; JSDoc Claim types only.

Typed component package sdk

  • Register components w/ TS prop types via ComponentPlugin contract.
  • <ClaimBadge claim={…} /> auto-completes; mistypes fail at build.
  • Component lifecycle hooks (mount, query-result, refresh).
// plugins/ik-components/index.ts export const plugin: ComponentPlugin = { components: { ClaimBadge, InitiativeCard, DeltaArrow }, schemas: { ClaimBadge: { claim: 'Claim', size: 'enum:sm|md|lg' } }, };
05Query runtime

DuckDB-WASM via fences today

  • All queries inside ```sql name fences in pages.
  • Templated only via Mustache {var[0].col}.
  • Can't run a query from a custom component or from JS.

Programmatic runQuery() sdk

  • $evidence/queries + runQuery() callable from Svelte / TS.
  • QuerySSR.svelte resolves queries server-side before hydration.
  • Auto-stamp run_id / started_at per execution via a custom runner.
// custom Svelte component import { runQuery } from '$evidence/queries'; const rows = await runQuery(` select * from claims where initiative_id = ${id} `);
06Build pipeline

CLI only (evidence build) today

  • Out-of-band Node + Python generators run before the CLI.
  • build_provenance.ts, build_indexes.ts, build_evidence_views.py all external scripts.
  • Failure of any external script = silently stale Evidence build.

Build is a library sdk

  • build-dev exposes phases: preBuild, generate, sources, compile, postBuild.
  • Register your generator as a phase. CLI calls it.
  • Single command, single failure surface, deterministic ordering.
  • Python materializers stay external — Node-only world.
07SSR / routing

SvelteKit defaults, no hooks today

  • A couple of +layout.svelte under pages/provenance/ already reach into SvelteKit — closest the project gets to SDK territory.
  • No request-scoped logic. Claim badges hydrate client-side via claimsManifest.js.

hooks.server.js + SSR claims sdk

  • Inject claim_id → Claim index server-side; no JS round-trip.
  • Auth, multi-tenant, claim-aware redirects (superseded claim → successor page).
  • Request-scoped query rewrites (e.g. tenant-filtered claims).
// src/hooks.server.ts import { evidenceHook } from '@evidence-dev/sdk/ssr'; export const handle = sequence( evidenceHook, async ({ event, resolve }) => { event.locals.claims = await loadClaims(); return resolve(event); } );
08Theming

evidence.config.yaml today

  • Palettes, colors, light/dark switcher in one YAML.
  • Per-claim or per-tier styling = manual class attributes in markdown.

Programmatic theme sdk

  • Mutate theme from generators (tier → palette mapping).
  • Claim-tier theming applied uniformly across all generated pages.
  • Typed theme schema; misspelled tokens fail at build.

§IWhere it intersects insight-kit

High-leverage already half-built
viz/evidence/generators/build_provenance.ts + build_indexes.ts are exactly what build-dev formalises. @insight-kit/viz-evidence already uses the implicit plugin loader. SDK adoption ≈ promoting existing scripts from out-of-band into registered build phases. ~70% of the seam is there.
The unlock that matters for the intervention loop
A custom insight-kit datasource plugin + build-dev page generator means: every record in initiatives_log.jsonl renders its own page, with frozen baseline + post-metric + delta + critic-verdict + critic-angle table, zero hand-editing. The founder dashboard is a Hamilton output. Add new initiative → next build → new page.

§DDecision shape

Adopt SDK only if the intervention-loop pilot ships and the next pain is "we are hand-curating one page per initiative". Until then, the current markdown surface is fine — markdown is a feature, not a liability, while scope is <15 levers. SDK pays off when the count of claim-driven pages exceeds the count of humans willing to keep them in sync.

Glossary · this page

Click any dotted term above to jump here.
DatasourcePlugin
SDK contract for custom connectors. Implements introspect() (list tables/cols), runQuery(sql, ctx) (execute), refresh hooks. Lets an insight-kit run directory become a first-class Evidence source w/o intermediate DuckDB rebuild.
ComponentPlugin
SDK contract for registering Svelte components w/ typed prop schemas. schemas entry declares each prop type; mistyped usage fails at build.
build-dev
SDK package exposing Evidence's dev/build pipeline as a library. Phases: preBuild, generate, sources, compile, postBuild. Register your generator as a phase instead of running it as an out-of-band script.
PageBuilder
Build-dev API for emitting .md pages at build time. PageBuilder.emit(path, body) writes a page; useful for one-per-claim or one-per-initiative outputs.
runQuery() / $evidence/queries
SDK module letting Svelte components / TS modules execute Evidence queries directly (not just inside ```sql fences). Returns typed result rows. Enables claim-aware logic in custom components.
QuerySSR.svelte
SDK component that resolves a query server-side and hands result to children pre-hydration. Cuts client-side query roundtrip; useful for above-the-fold KPIs.
ssrHook / hooks.server.js
SvelteKit's request-handling extension point. SDK exposes evidenceHook; you compose it w/ your own to inject per-request locals (auth, tenant filter, claim index).
SvelteKit
The meta-framework Evidence is built on. +page.svelte, +layout.svelte, hooks.server.js are SvelteKit files. SDK adoption pulls you closer to raw SvelteKit knowledge.
SQL fence
Markdown code block ```sql name ... ``` in an Evidence page. Defines a named query whose result is bound to {name} in the page scope. Today's primary authoring surface.
Mustache interpolation
Evidence's {var[0].col} syntax for inlining query result fields into prose or component props. Limited to literal substitution; no logic.
Generator
A build-time script (TS or Python) that emits artefacts before Evidence compiles. Today: build_provenance.ts, build_indexes.ts, build_evidence_views.py — all out-of-band. SDK promotes them to registered build phases.
@insight-kit/viz-evidence
Local npm workspace dep at ../../insight-kit/viz/evidence. Exposes Svelte components + a generators/ dir. Already uses Evidence's implicit plugin loader; 70% of the SDK seam is here.
claimsManifest.js
JS helper at reports/components/claimsManifest.js. Provides indexClaims() + getClaim() to look up a claim by ID inside a page. Client-side only today; SSR via ssrHook removes the round-trip.
introspect()
Method on a DatasourcePlugin that returns the source's schema (tables, columns, types). Evidence uses it to autocomplete SQL + validate fences at build time.
Fingerprint
Hash of (code + inputs + config) used as a cache key. Hamilton's caching adapter uses this for node-level recompute decisions. Cross-page term — see cache-walkthrough.html.
