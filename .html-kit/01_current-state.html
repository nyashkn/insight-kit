insight-kit, as it actually runs today.

Before the Hamilton refactor: what does an analyst loop look like on disk? This page walks the lifecycle, then peels open 6 real runs from your-business/consumer-repo/data/agent_runs/ — Shopify ingest, Meta worker, analyst council, critic, initiative wiring — so a newcomer can read one page and understand the shape insight-kit is asking Hamilton to compose with.

ik bootstrap→ declare goal→ with Run(...)→ ingest input→ emit metric→ claim(...)→ Layer A/B→ preflight→ Evidence.dev

§1The lifecycle in one breath

insight-kit lives at your-business/consumer-repo/src/consumer-repo/provenance/. The unit of work is a Run: a topic + agent + timestamped directory under data/agent_runs/<run_id>/. Inside one Run, the analyst (a) imports Run, (b) opens a context, (c) ingests inputs, (d) computes, (e) emits parquet artifacts, (f) emits typed claims, (g) closes the context. The close writes manifest.json, claims.jsonl, checksums.sha256, env.lock, and a verbatim copy of script.py. Validation (Layers A/B/C) runs inline + post-hoc. 

  # the canonical idiom (paraphrased from real scripts)
  from consumer-repo.provenance import Run

  with Run(topic="shopify_orders_bulk", agent="human") as run:
      orders_df = run.ingest_jsonl("data/raw/shopify/orders_bulk.jsonl")
      orders, line_items = split_orders_and_line_items(orders_df)
      run.emit_metric("orders.parquet", orders)
      run.emit_metric("line_items.parquet", line_items)
      run.claim(id="SHOPIFY_ORDERS_TOTAL",
                statement="total orders (all statuses, all-time)",
                value=len(orders), unit="count",
                evidence_ref="orders.parquet#row_count",
                confidence="high")
The four objects on disk
manifest.json = run header + InputRecord/OutputRecord/ApiCall list + code SHA + git state + runtime telemetry. claims.jsonl = one claim per line. checksums.sha256 = sha256 of every output artifact (post-emit recomputed). env.lock = pip freeze at run open. Together: a self-describing, reproducible bundle.

§2The four layers of claims

Claims are not all the same kind of statement. The taxonomy below is enforced by provenance/claim.py (ClaimTier enum) and read by the Evidence.dev seam to colour charts and build the lineage view. Real claim IDs from data/agent_runs/2026-04-24_0608_analyst_g1_spend_reallocation/claims.jsonl shown inline.

raw / etl_raw

Ingest layer — what hit disk verbatim

Counts of records pulled from an external API or file. Produced by ingest scripts. No interpretation; the claim is "we received N rows".

e.g. SHOPIFY_ORDERS_TOTAL = 8993 · SHOPIFY_LINE_ITEMS_TOTAL = 10671
derived / etl_metric

Metric layer — what the analyst computed

Quantitative findings. Statement + value + confidence + cites. The analyst owns these.

e.g. MD-D-001: "45-54 male ROAS collapsed 6.9x → 2.0x (Mar → Apr 2025)" · MD-D-002: "25-34 male is starved winner at 11.1x ROAS"
critic

Critic layer — what's wrong with the metric

Falsification attempt against a target derived claim. Requires target + challenge_type + verdict + severity. Layer-A rule: every critic claim must carry at least one supports/refutes edge.

e.g. MD-C-001 challenges MD-D-001 (confounder, weakening) · MD-C-003 challenges MD-D-002 (AOV anomaly, blocking)
initiative / viz / counterfactual

Action layer — what we are going to do, show, simulate

Initiatives are logged separately to data/initiatives_log.jsonl; viz claims point at chart artifacts; counterfactuals model "what if". Cross-referenced via claim_refs.

e.g. G4-2026-05-04 (suppress past buyers from active adsets, baseline CPA 1617 KES) · F7-2026-05-05 (refresh exclusion audience)

§3Validation — two orthogonal axes

insight-kit's checks come in two unrelated families that both happen to be numbered. This trips up newcomers. Layer A/B/C is about claim correctness; Layer 1–6 is about run completeness. They share no implementation; they don't refer to each other.

claim correctness

Layer A / B / C

A — real-time, per Run. Claim-ID regex (^[A-Z]{2,5}-(D|R|C|I|V|X|ETL_[RCM])-\d{3,}$), namespace match, referential integrity of input_claims, critic-edge rule, external-caveat rule.
B — post-Run, repo-wide. Global uniqueness of claim IDs (unless a supersedes chain exists).
C — cross-project, via ik validate. Scans many runs across the filesystem; catches drift between sibling projects.

run completeness

Layer 1 – 6 (preflight)

Run via scripts/preflight_check.py. Six independent checks:
1 schema validity · 2 run integrity (manifest ↔ disk) · 3 claim coverage (every goal has a claim) · 4 evidence density (claims per goal threshold) · 5 evidence viz (every promoted claim has a chart) · 6 skill availability (skills-lock.json present + intact).

Naming hazard
Don't conflate them. "Layer A" is a property of a claim; "Layer 1" is a property of a run. The Hamilton refactor only touches Layer A/B/C (it relocates them into validator adapters). Layer 1–6 stays as a CLI step.

Take-away
insight-kit today is filesystem-first. Every Run is a directory; every claim is one line of JSONL; every artifact is parquet with a sibling schema + sha. The Hamilton refactor must preserve this on-disk contract — Evidence.dev consumes the directory tree, not the Python API. Everything in this page (manifests, claims, validation, the warehouse seam) stays. What changes is who writes them: a Hamilton lifecycle hook instead of a hand-sequenced script.py.

Glossary · this page

Dotted terms above jump here.
Run
The unit of work in insight-kit. A timestamped directory under data/agent_runs/<run_id>/ that records a topic, agent, all inputs, all outputs, and all claims produced in one execution context.
agent_runs/
Root directory holding every Run produced by the project: your-business/consumer-repo/data/agent_runs/. 45 runs as of 2026-05-14; Evidence.dev and DuckDB treat this as a single queryable timeline.
manifest.json
Written at Run close. Contains: run header (topic, agent, timestamps), InputRecord[], OutputRecord[], ApiCall[], code SHA, git state, and runtime telemetry. The authoritative record of what a Run did.
claims.jsonl
One JSON object per line, written at Run close. Each line is one typed claim (raw, derived, critic, initiative, viz). The file is append-only during a Run and validated by Layer A before close.
env.lock
pip freeze output captured at Run open. Ensures the exact Python environment is recorded alongside every artifact, enabling exact replay.
checksums.sha256
SHA-256 digests of every output artifact, recomputed post-emit. Used by Layer 2 (run integrity) to detect tampering or partial writes between runs.
parquet
Columnar binary format used for all output artifacts (orders, line_items, ad metadata, hashed buyers). Each parquet file travels with a sibling .schema.json and a sha entry in checksums.sha256.
ClaimTier
Python enum in provenance/claim.py enforcing four mutually exclusive tiers: raw (etl_raw), derived (etl_metric / analyst), critic, and initiative / viz / counterfactual. Evidence.dev uses tier to colour charts and build lineage views.
Evidence.dev
The BI / reporting layer. Reads DuckDB views built from the agent_runs/ tree, renders Markdown + SQL fences as interactive dashboards. The Hamilton refactor must keep the on-disk contract Evidence.dev depends on intact.
initiatives_log.jsonl
Project-level index of all active and past initiatives at data/initiatives_log.jsonl. Each row carries a claim_id prefix, baseline metric, checkpoint date, and status. The run dir is the audit trail; this log is the searchable index.
baseline claim
A metric value recorded at initiative launch (e.g. blended_purchase_cpa_kes = 1617 for G4). Stored in initiatives_log.jsonl and cited by verdict claims to compute delta after the checkpoint date.
council persona
Named analyst / critic identities (e.g. feynman for analyst, kahneman for critic) whose prompt files are versioned in-tree alongside the run. Ensures the LLM persona that produced a claim is auditable.
Layer A / B / C
Claim-correctness validation family. A = real-time per Run (ID regex, namespace, referential integrity, critic-edge). B = post-Run, repo-wide uniqueness. C = cross-project via ik validate. Distinct from Layer 1–6.
Layer 1–6 (preflight)
Run-completeness checks executed by scripts/preflight_check.py: schema validity, run integrity, claim coverage, evidence density, evidence viz, and skill availability. Runs as a CLI step; unrelated to Layer A/B/C.
namespace
The two-to-five uppercase letter prefix of a claim ID indicating which project / agent family owns it (e.g. NM = NairoMarket initiative, MD = Meta Derived, DOCK = Dockware). Layer A validates that a claim's namespace matches its run's configured project.
input_claims
Field on a derived or critic claim listing the upstream claim IDs it depends on. Layer A checks referential integrity: every ID in input_claims must exist in the corpus at write-time.
supersedes
Optional field on a claim that points to an older claim ID it replaces. Layer B allows duplicate claim IDs if a supersedes chain can be traced. Used when a revised analysis invalidates a prior finding.
goal
A named analytical objective declared in .insight-kit/goals/. Layer 3 (preflight) checks that every goal has at least one claim. Goals provide the topic axis that groups runs and organises Evidence pages.
.insight-kit/
Hidden config directory at the project root (the "kit root"). Holds goal declarations, skills-lock, and project metadata. Discovered by walking up the directory tree from the current working directory.
DuckDB
In-process analytical engine powering the warehouse at data/warehouse.duckdb. Views over the agent_runs/ parquet tree are built by build_duckdb_views.py and queried directly by Evidence.dev SQL fences.
build_duckdb_views.py
Script at scripts/build_duckdb_views.py that scans all run output directories, registers parquet files as DuckDB views, and writes data/warehouse.duckdb. Runs out-of-band before evidence build; the Hamilton refactor may promote it to a registered build phase.
