Agentic-coding observability is not LLM observability.

14 platforms scored 8 axes OSS-self-host bias Bun-runtime aware For oh-my-pi / omp

Throughout 2026 the field finally split. LLM observability still treats a request as the unit. Agent observability treats a run as the unit — an analyst + N code sub-agents + critic + judge, all rolled under one trace id. The platforms that grew up agent-first don't look like Langfuse + a span tree; they look like transcripts, agent graphs, and replay buttons. Here's how 14 contenders score for an omp harness on Bun/TS + Python/Hamilton, and which ones survive the Bun runtime tax.

§1Eight axes that decide it for omp

Pick the right scoring rubric and the answer almost writes itself. For a containerized omp harness driving one analyst + N code sub-agents + one critic + one future judge per run, eight axes matter — license, agent-first design, parent/child rollup under a single run-id, dual TS+Python SDKs, built-in agent-as-judge, replay, Bun compatibility, and a path to Harbor RL.

Axis 01–02

License + self-host

Single-container deploy ideal. Apache/MIT preferred. ELv2 is OK for self-host, blocks reselling.

Axis 03

Agent-first

Not "LLM proxy with sessions". Modelled around agent run → sub-agent → tool call.

Axis 04

Run-id rollup

1 analyst spawns N coders. All spans aggregate under one parent.

Axis 05

TS + Python SDK

Bun for omp, Python for Hamilton DAG. Both must emit into the same trace.

Axis 06

Agent-as-judge

Critic + judge live inside the platform — or at least its eval primitives.

Axis 07–08

Bun + Harbor

Bun's OTel auto-instrumentation is fragile. Harbor RL expects trajectory shape, not OTLP.

§3What's actually new in 2026

01

OTel GenAI conventions hit v5

Pydantic's instrumentation iterated through five spec versions in 12 months. gen_ai.input.messages, pydantic_ai.all_messages, and agent-run spans are now stable. Backend choice = UX choice, not wire-protocol lock-in [4].

02

OpenInference TypeScript 2.0

Nov 2025 release shipped @observe decorators, function-tracing wrappers, attribute helpers — Phoenix TS finally has Python parity [29].

03

Agent-as-judge goes mainstream

Galileo's Luna-2 (fine-tuned Llama-3B/8B) runs 10–20 metrics at 152 ms, 97% cheaper than GPT-4o LLM-judge. Maxim, Opik, Patronus, HoneyHive, Braintrust all ship LLM-judge primitives [32].

04

Dynatrace ships named-agent integrations

April/May 2026: Claude Code, Codex CLI, Gemini CLI, OpenCode, Copilot SDK as first-class. Signals "Big-Three APM cares" market maturity [11].

05

Laminar's transcript-first UI

Explicitly rejects span tree as default. Agent conversation + tool calls render as transcript; span tree on demand. Most agent-native UX redesign of the year [3].

06

Braintrust MCP for IDE observability

Cursor / Claude Code / VS Code query trace data directly. First time observability is consumed by the coding agent, not just emitted by it [34].

§4The Bun runtime tax

⚠ Load-bearing gotcha

Bun + OpenTelemetry auto-instrumentation is still partly broken on Bun 1.3.7 (May 2026). Don't rely on it. Use programmatic NodeSDK init and wrap spans by hand.

FastifyInstrumentation / ExpressInstrumentation hooks no-op

Bun issue #26536: requestHook never fires; span names degenerate to bare GET/POST; per-route filtering becomes impossible [8].

Phoenix TS client logs per-request errors

otel-js #5260: payloads arrive on the server, but the JS client throws on every send under Bun. Node engine works clean [10].

@opentelemetry/instrumentation-fs crashes

Known Bun-crasher. Disable explicitly via getNodeAutoInstrumentations({ '@opentelemetry/instrumentation-fs': { enabled: false } }) [9].

Bun.serve() / bun:sqlite not auto-instrumented

Built-in Bun APIs are invisible. Wrap manually with @opentelemetry/api — the cost is real but bounded.

Practical takeaway for omp: wrap the analyst loop + each sub-agent + critic + judge in tracer.startActiveSpan() calls with explicit run.id attribute. Don't trust auto-instrumentation to nest them for you. --require doesn't work reliably; programmatic init at top of entry.ts is mandatory [37][38].

§5Path to Harbor RL

Harbor (Jan 2026) is a containerized agent-eval + RL-environment framework — omp's eventual destination for fine-tuning scored runs [39][40]. Native OTel ingestion is not documented as of May 2026. Best path:

  • Export omp traces as structured JSONL (one event per line, run-id + span hierarchy preserved). Harbor's RL pipeline expects trajectory-shaped data, not OTLP wire format.
  • Borrow Braintrust's BraintrustSpanProcessor pattern — converts OTel spans → structured agent traces [2]. Fork to emit Harbor-shaped (state, action, observation, reward) tuples.
  • OpenRLHF 0.10 (April 2026) added multi-turn VLM RL [41]. Harbor will follow that shape. Plan replay = trajectory tuples derived from your trace.

§6Recommendation — three tiers for omp

Tier 1

Langfuse OSS + OpenTelemetry GenAI + Hamilton's existing Python tracing

Single-container Langfuse via official Docker. omp emits OTLP via Bun-friendly manual spans. Hamilton DAG emits the same OTLP from Python. One trace per run-id; analyst is root span; sub-agents are children; critic + judge are sibling spans tied to the same trace. This is the boring, working, MIT-licensed answer — and pi-flavoured projects already integrate Langfuse via the official Claude Code Stop hook [memory].

Tier 2

Add Comet Opik alongside Langfuse

Apache-2.0, runs in the same docker-compose.yml, dual-emits the OTLP. Gives you the agent-graph view + GEPA optimizer + Hamilton-friendly span schema. Best ROI for analyst/critic/judge structure because Opik specifically models multi-step reasoning paths and ships built-in LLM-judge.

Tier 3

Swap Bun → Node for the omp host process if pain dominates

Keep Bun for tool execution; run the long-lived omp orchestrator on Node. Bun's OTel hostile-environment cost is ~2 days of debug per Bun upgrade. Worth the swap if you're shipping to production teams in 2026; not worth it for an internal harness you control.

Don't pick

Patronus (K8s-only commercial), Maxim (no self-host), Galileo (eval gated to enterprise), HoneyHive (BYOC = enterprise), Dynatrace (no free tier). All are excellent products. None fit a single-container OSS harness.

§710-minute proof of concept

Langfuse + Opik dual-emit, one run id, full analyst→sub-agent→critic→judge rollup.

# 1. docker-compose.yml — both backends, both OTLP on 4318
services:
  langfuse: { image: langfuse/langfuse:3, ports: ["3000:3000", "4318:4318"] }
  opik:     { image: comet/opik:latest,    ports: ["5173:5173", "4319:4318"] }

# 2. omp entry.ts — programmatic OTel init BEFORE any imports
import { NodeSDK }            from '@opentelemetry/sdk-node'
import { OTLPTraceExporter }  from '@opentelemetry/exporter-trace-otlp-http'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'

new NodeSDK({
  spanProcessors: [
    new BatchSpanProcessor(new OTLPTraceExporter({ url: 'http://langfuse:4318/v1/traces' })),
    new BatchSpanProcessor(new OTLPTraceExporter({ url: 'http://opik:4318/v1/traces' })),
  ],
  instrumentations: [getNodeAutoInstrumentations({
    '@opentelemetry/instrumentation-fs': { enabled: false },  // Bun crash workaround
  })],
}).start()

# 3. wrap the run
const tracer = trace.getTracer('omp')
await tracer.startActiveSpan('omp.run', { attributes: { 'run.id': runId } }, async (root) => {
  await runAnalyst(runId)         // emits child spans
  for (const t of tasks) await spawnCodeAgent(runId, t)  // each child of root
  await runCritic(runId)
  await runJudge(runId)
  root.end()
})

# 4. Hamilton (Python) — propagate run_id via W3C traceparent env
from opentelemetry import trace
tracer = trace.get_tracer("hamilton")
with tracer.start_as_current_span("hamilton.dag", attributes={"run.id": run_id}):
    driver.execute([...])

# 5. visit http://localhost:3000 (Langfuse span tree)
#          http://localhost:5173 (Opik agent-graph + judge scores)

Wall-clock: ~10 min config, ~30 min to a first clean trace including critic + judge attribution under the same run id.

§8Killer gotchas, rank-ordered

  1. Bun + OTel auto-instrumentation is broken in subtle ways — span names degenerate, FS crashes, Phoenix logs per-request errors. Manual spans only. [8][9][10]
  2. Double-counted tokens — parent + child both report gen_ai.usage.*. Datadog / Opik / New Relic sum them. Set use_aggregated_usage_attribute_names or pre-divide. [4]
  3. "Self-host" ≠ free self-host — AgentOps, HoneyHive, Maxim, Galileo, Patronus all gate self-host behind Enterprise pricing. Free self-host: Langfuse, Opik, Laminar, Phoenix, Logfire SDK (not backend), Inkeep. [22][35]
  4. Phoenix is ELv2, not MIT/Apache — fine for self-host; forbidden if you ship a hosted SaaS competing with Arize Cloud. Reads as Apache at a glance; it isn't. [28]
  5. Helicone is maintenance-mode under Mintlify in 2026 — don't bet long-term. [36]
  6. Maxim free-tier retention is 3 days — useless for post-hoc incident debug. [18]
  7. OpenInference TS 2.0 decorators need useDefineForClassFields: true — Bun's tsconfig defaults can break decorator span creation. [29]
  8. LangSmith Agent Replay is closed-beta + LangChain-coupled — reference only.
Deep cut — why "agent-first" actually matters (and why span-tree-as-default fails)

The conceptual leap in 2026 is that agent traces are not shaped like distributed-systems traces. A microservice trace is a fan-out of independent calls; an agent trace is a causally coupled sequence where step 3's tool output conditions step 8's reasoning. A failure at step 3 that silently corrupts the chain through step 8 is invisible to call-level monitoring and only detectable in a full-session view.

This is why Laminar's transcript-first UI matters: humans read agent runs as conversations, not as flame graphs. The span tree is still there when you need to drill into a specific tool call, but the default rendering matches the mental model of what's happening. AgentOps and Phoenix get partway there with agent-graph visualization; Langfuse and Helicone retrofit the data into LLM-monitoring widgets.

For omp specifically: the analyst's reasoning loop calls N code sub-agents, each of which makes M tool calls. A span-tree of N×M nodes is unreadable. A transcript of "analyst said X → sub-agent 3 ran tool Y → critic said Z" is readable. Pick the UX that matches your reading mode.

Decision

Ship Langfuse + Opik dual-emit. Plan Harbor JSONL export. Pay the Bun manual-instrumentation tax.

  1. Trace backbone: Langfuse OSS in the harness container. Single source of truth for spans + token cost.
  2. Agent UX + judge: Comet Opik in the same compose file. Agent-graph + LLM-judge for critic alignment.
  3. Run-id rollup: wrap analyst, every sub-agent, critic, judge in explicit tracer.startActiveSpan() calls with run.id attribute. Don't trust Bun auto-instrumentation.
  4. Harbor path: add a HarborSpanProcessor that converts OTel spans → JSONL trajectories. Forked from Braintrust's pattern.
  5. Revisit in 6 months: if Laminar's Bun support stabilises, swap Opik → Laminar for the transcript-first UI win.

Top recommendation in one sentence: stack Langfuse OSS (MIT) for the trace backbone with Comet Opik (Apache-2.0) on the same compose file for the agent-graph + agent-as-judge — both ride the OTel GenAI spec, both run in one container, neither charges for self-host.
