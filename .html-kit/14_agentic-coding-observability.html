Agentic-coding observability is not LLM observability.

14 platforms scored 8 axes OSS-self-host bias Bun-runtime aware For oh-my-pi / omp

Throughout 2026 the field finally split. LLM observability still treats a request as the unit. Agent observability treats a run as the unit — an analyst + N code sub-agents + critic + judge, all rolled under one trace id. The platforms that grew up agent-first don't look like Langfuse + a span tree; they look like transcripts, agent graphs, and replay buttons. Here's how 14 contenders score for an omp harness on Bun/TS + Python/Hamilton, and which ones survive the Bun runtime tax.

§1Eight axes that decide it for omp

Pick the right scoring rubric and the answer almost writes itself. For a containerized omp harness driving one analyst + N code sub-agents + one critic + one future judge per run, eight axes matter — license, agent-first design, parent/child rollup under a single run-id, dual TS+Python SDKs, built-in agent-as-judge, replay, Bun compatibility, and a path to Harbor RL.

Axis 01–02

License + self-host

Single-container deploy ideal. Apache/MIT preferred. ELv2 is OK for self-host, blocks reselling.

Axis 03

Agent-first

Not "LLM proxy with sessions". Modelled around agent run → sub-agent → tool call.

Axis 04

Run-id rollup

1 analyst spawns N coders. All spans aggregate under one parent.

Axis 05

TS + Python SDK

Bun for omp, Python for Hamilton DAG. Both must emit into the same trace.

Axis 06

Agent-as-judge

Critic + judge live inside the platform — or at least its eval primitives.

Axis 07–08

Bun + Harbor

Bun's OTel auto-instrumentation is fragile. Harbor RL expects trajectory shape, not OTLP.

§3What's actually new in 2026

01

OTel GenAI conventions hit v5

Pydantic's instrumentation iterated through five spec versions in 12 months. gen_ai.input.messages, pydantic_ai.all_messages, and agent-run spans are now stable. Backend choice = UX choice, not wire-protocol lock-in [4].

02

OpenInference TypeScript 2.0

Nov 2025 release shipped @observe decorators, function-tracing wrappers, attribute helpers — Phoenix TS finally has Python parity [29].

03

Agent-as-judge goes mainstream

Galileo's Luna-2 (fine-tuned Llama-3B/8B) runs 10–20 metrics at 152 ms, 97% cheaper than GPT-4o LLM-judge. Maxim, Opik, Patronus, HoneyHive, Braintrust all ship LLM-judge primitives [32].

04

Dynatrace ships named-agent integrations

April/May 2026: Claude Code, Codex CLI, Gemini CLI, OpenCode, Copilot SDK as first-class. Signals "Big-Three APM cares" market maturity [11].

05

Laminar's transcript-first UI

Explicitly rejects span tree as default. Agent conversation + tool calls render as transcript; span tree on demand. Most agent-native UX redesign of the year [3].

06

Braintrust MCP for IDE observability

Cursor / Claude Code / VS Code query trace data directly. First time observability is consumed by the coding agent, not just emitted by it [34].

§4The Bun runtime tax

⚠ Load-bearing gotcha

Bun + OpenTelemetry auto-instrumentation is still partly broken on Bun 1.3.7 (May 2026). Don't rely on it. Use programmatic NodeSDK init and wrap spans by hand.

FastifyInstrumentation / ExpressInstrumentation hooks no-op

Bun issue #26536: requestHook never fires; span names degenerate to bare GET/POST; per-route filtering becomes impossible [8].

Phoenix TS client logs per-request errors

otel-js #5260: payloads arrive on the server, but the JS client throws on every send under Bun. Node engine works clean [10].

@opentelemetry/instrumentation-fs crashes

Known Bun-crasher. Disable explicitly via getNodeAutoInstrumentations({ '@opentelemetry/instrumentation-fs': { enabled: false } }) [9].

Bun.serve() / bun:sqlite not auto-instrumented

Built-in Bun APIs are invisible. Wrap manually with @opentelemetry/api — the cost is real but bounded.

Practical takeaway for omp: wrap the analyst loop + each sub-agent + critic + judge in tracer.startActiveSpan() calls with explicit run.id attribute. Don't trust auto-instrumentation to nest them for you. --require doesn't work reliably; programmatic init at top of entry.ts is mandatory [37][38].

§5Path to Harbor RL

Harbor (Jan 2026) is a containerized agent-eval + RL-environment framework — omp's eventual destination for fine-tuning scored runs [39][40]. Native OTel ingestion is not documented as of May 2026. Best path:

  • Export omp traces as structured JSONL (one event per line, run-id + span hierarchy preserved). Harbor's RL pipeline expects trajectory-shaped data, not OTLP wire format.
  • Borrow Braintrust's BraintrustSpanProcessor pattern — converts OTel spans → structured agent traces [2]. Fork to emit Harbor-shaped (state, action, observation, reward) tuples.
  • OpenRLHF 0.10 (April 2026) added multi-turn VLM RL [41]. Harbor will follow that shape. Plan replay = trajectory tuples derived from your trace.

§6Recommendation — three tiers for omp

Superseded by §9–§13

The three-tier framing below is the original May 2026 recommendation, kept for traceability. After fetching Laminar and Opik at HEAD (§9) and walking the actual interaction flow + deploy topology (§10, §12), the single-platform answer in the Decision block is Laminar, not Langfuse+Opik dual-emit. Read this section as context; treat §9 onward as the live recommendation.

Tier 1

Langfuse OSS + OpenTelemetry GenAI + Hamilton's existing Python tracing

Single-container Langfuse via official Docker. omp emits OTLP via Bun-friendly manual spans. Hamilton DAG emits the same OTLP from Python. One trace per run-id; analyst is root span; sub-agents are children; critic + judge are sibling spans tied to the same trace. This is the boring, working, MIT-licensed answer — and pi-flavoured projects already integrate Langfuse via the official Claude Code Stop hook [memory].

Tier 2

Add Comet Opik alongside Langfuse

Apache-2.0, runs in the same docker-compose.yml, dual-emits the OTLP. Gives you the agent-graph view + GEPA optimizer + Hamilton-friendly span schema. Best ROI for analyst/critic/judge structure because Opik specifically models multi-step reasoning paths and ships built-in LLM-judge.

Tier 3

Swap Bun → Node for the omp host process if pain dominates

Keep Bun for tool execution; run the long-lived omp orchestrator on Node. Bun's OTel hostile-environment cost is ~2 days of debug per Bun upgrade. Worth the swap if you're shipping to production teams in 2026; not worth it for an internal harness you control.

Don't pick

Patronus (K8s-only commercial), Maxim (no self-host), Galileo (eval gated to enterprise), HoneyHive (BYOC = enterprise), Dynatrace (no free tier). All are excellent products. None fit a single-container OSS harness.

§710-minute proof of concept

Langfuse + Opik dual-emit, one run id, full analyst→sub-agent→critic→judge rollup.

# 1. docker-compose.yml — both backends, both OTLP on 4318
services:
  langfuse: { image: langfuse/langfuse:3, ports: ["3000:3000", "4318:4318"] }
  opik:     { image: comet/opik:latest,    ports: ["5173:5173", "4319:4318"] }

# 2. omp entry.ts — programmatic OTel init BEFORE any imports
import { NodeSDK }            from '@opentelemetry/sdk-node'
import { OTLPTraceExporter }  from '@opentelemetry/exporter-trace-otlp-http'
import { BatchSpanProcessor } from '@opentelemetry/sdk-trace-base'

new NodeSDK({
  spanProcessors: [
    new BatchSpanProcessor(new OTLPTraceExporter({ url: 'http://langfuse:4318/v1/traces' })),
    new BatchSpanProcessor(new OTLPTraceExporter({ url: 'http://opik:4318/v1/traces' })),
  ],
  instrumentations: [getNodeAutoInstrumentations({
    '@opentelemetry/instrumentation-fs': { enabled: false },  // Bun crash workaround
  })],
}).start()

# 3. wrap the run
const tracer = trace.getTracer('omp')
await tracer.startActiveSpan('omp.run', { attributes: { 'run.id': runId } }, async (root) => {
  await runAnalyst(runId)         // emits child spans
  for (const t of tasks) await spawnCodeAgent(runId, t)  // each child of root
  await runCritic(runId)
  await runJudge(runId)
  root.end()
})

# 4. Hamilton (Python) — propagate run_id via W3C traceparent env
from opentelemetry import trace
tracer = trace.get_tracer("hamilton")
with tracer.start_as_current_span("hamilton.dag", attributes={"run.id": run_id}):
    driver.execute([...])

# 5. visit http://localhost:3000 (Langfuse span tree)
#          http://localhost:5173 (Opik agent-graph + judge scores)

Wall-clock: ~10 min config, ~30 min to a first clean trace including critic + judge attribution under the same run id.

§8Killer gotchas, rank-ordered

  1. Bun + OTel auto-instrumentation is broken in subtle ways — span names degenerate, FS crashes, Phoenix logs per-request errors. Manual spans only. [8][9][10]
  2. Double-counted tokens — parent + child both report gen_ai.usage.*. Datadog / Opik / New Relic sum them. Set use_aggregated_usage_attribute_names or pre-divide. [4]
  3. "Self-host" ≠ free self-host — AgentOps, HoneyHive, Maxim, Galileo, Patronus all gate self-host behind Enterprise pricing. Free self-host: Langfuse, Opik, Laminar, Phoenix, Logfire SDK (not backend), Inkeep. [22][35]
  4. Phoenix is ELv2, not MIT/Apache — fine for self-host; forbidden if you ship a hosted SaaS competing with Arize Cloud. Reads as Apache at a glance; it isn't. [28]
  5. Helicone is maintenance-mode under Mintlify in 2026 — don't bet long-term. [36]
  6. Maxim free-tier retention is 3 days — useless for post-hoc incident debug. [18]
  7. OpenInference TS 2.0 decorators need useDefineForClassFields: true — Bun's tsconfig defaults can break decorator span creation. [29]
  8. LangSmith Agent Replay is closed-beta + LangChain-coupled — reference only.
Deep cut — why "agent-first" actually matters (and why span-tree-as-default fails)

The conceptual leap in 2026 is that agent traces are not shaped like distributed-systems traces. A microservice trace is a fan-out of independent calls; an agent trace is a causally coupled sequence where step 3's tool output conditions step 8's reasoning. A failure at step 3 that silently corrupts the chain through step 8 is invisible to call-level monitoring and only detectable in a full-session view.

This is why Laminar's transcript-first UI matters: humans read agent runs as conversations, not as flame graphs. The span tree is still there when you need to drill into a specific tool call, but the default rendering matches the mental model of what's happening. AgentOps and Phoenix get partway there with agent-graph visualization; Langfuse and Helicone retrofit the data into LLM-monitoring widgets.

For omp specifically: the analyst's reasoning loop calls N code sub-agents, each of which makes M tool calls. A span-tree of N×M nodes is unreadable. A transcript of "analyst said X → sub-agent 3 ran tool Y → critic said Z" is readable. Pick the UX that matches your reading mode.

§9Laminar vs Opik — the 7-axis cage match

Both ship Apache-2.0 source. Both run in Docker on a Tailnet box. Both speak OTel. The differences are where the platform wants you to look — Opik wants you in a scorer library; Laminar wants you in a transcript. For the omp shape (one analyst spawning N coders, one critic, one judge, scored by a structural-then-semantic grader), one of these mismatches dominates. The other lives with itself.

The hinge

Opik wins decisively on axes 2 and 3. That matters only if we believe the built-in scorer library is doing the load-bearing work for D01. It isn't — D01's three checks (claim_id regex, citation cross-validation, length-distribution prior) are all custom scorers we'd write either way, because they encode this project's claim schema, not a generic LLM eval. Opik's RegexMatch and IsJson are too coarse; we need RegexMatch(pattern=r'^MD-[DC]-G\d-\d{3}$', field='claim_id') and citation in run.queries, which is a custom Python class in either platform. The 30-scorer library is a marketing artifact, not a use-case match.

Per-axis paragraph reasoning — why each cell lands where it lands

Axis 1 (trace backbone). Both ingest OTLP cleanly. The differentiator is the default render. Opik shows a span tree by default — fine for a 50-span request, hostile for a 2,000-span agent run with N×M tool calls. Laminar shows a transcript by default — analyst bubble, sub-agent bubble, critic bubble, judge bubble — and the span tree is one click away. For an omp run that already has six discovered tasks (D01–D04 + B1) we'll need to read by trajectory, not by latency flame graph. Laminar's render matches our reading mode.

Axis 2 (agent-as-judge). Opik ships a real scorer library: 30+ built-in metrics including Hallucination, G-Eval, Trajectory Accuracy, Agent Task Completion Judge, plus heuristics like RegexMatch, IsJson, Equals, Levenshtein. Laminar's eval story is admittedly thinner — Laminar's own competitive article concedes "Langfuse and Braintrust have stronger eval harnesses than Laminar" — and instead leans on Signals: natural-language outcome descriptions that backfill across trace history. For our D01 hardening this is a wash: we are writing custom scorers either way (claim_id regex needs our exact pattern, citation cross-check needs our queries/ dir, length prior needs our 12KB baseline). For drift detection it's a Laminar win: "alert when the critic stops disagreeing" is exactly what Signals describes.

Axis 3 (datasets + experiments). This is Opik's strongest axis. The D02 factorial (AGENT × CHANNEL × MODEL, 8 cells, k=3 trials) has a textbook Opik representation: one Dataset (the 8 prompts × 3 repeats = 24 items), one Experiment (the run), an execution-policy of {trials: 3, must_pass: 2}, side-by-side comparison UI. Laminar Datasets exist and you can bulk-create from SQL, but the factorial → comparison-UI workflow is less prefab. The mitigation: Laminar's SQL interface means "show me drop rate per CHANNEL marginalized over AGENT, MODEL" is one query — we don't need a comparison UI, we need a SQL prompt. Opik wins the convenience; Laminar matches the capability via a different idiom.

Axis 4 (deploy fit). Laminar's 6 services vs Opik's 11 is a real number, and it's the load-bearing one. Opik needs MySQL and Redis and Zookeeper and ClickHouse and MinIO and four app containers. On a single Tailnet host with the harness + Hamilton + Infisical edge already running, that's a non-trivial memory + disk footprint. Laminar's stack (Postgres + ClickHouse + Quickwit + 2 app containers) is roughly half the surface area. The Opik footprint also pulls in a Java backend (heavier JVM footprint than Laminar's Rust app-server) and a separate Python backend for scorers (sandboxed code execution). For a long-lived self-hosted box that's not the harness's primary purpose, fewer containers means fewer things to watch.

Axis 5 (early-flag UX). Both platforms can fire alerts on score thresholds. The difference is how the alert is described. Opik's "score < 0.5 on G-Eval" requires you to define the G-Eval. Laminar's Signals let you write "the critic stopped finding contradictions" in plain language and the platform back-classifies historical traces. For an omp harness that will run hundreds of times over the next year, the cost of writing a scorer for every drift mode is higher than the cost of writing a Signal. The transcript view also makes the token cliff visually obvious: the analyst's bubble narrows as the conversation goes on. In a span tree that's a column you have to know to look at.

Axis 6 (Bun reality). Honest answer: neither has a Bun success story at the URL level. Neither has a Bun-tagged issue at the repo level. Both ride the standard @opentelemetry/sdk-node path, which means both inherit the same Bun pain we'd hit with Langfuse or Phoenix. Both will work if we hand-wrap spans via tracer.startActiveSpan() (which we have to do anyway — see §4). Both will break the same way if we trust auto-instrumentation. This axis is a wash, and the resolution is the same regardless of pick: manual spans, programmatic NodeSDK init, FS instrumentation disabled.

Axis 7 (Harbor JSONL). Laminar exposes a SQL interface over the trace store. Harbor wants (state, action, observation, reward) tuples. Both representations are tabular. A single query — SELECT span_id, parent_id, attributes['gen_ai.input.messages'], attributes['gen_ai.output.messages'], score FROM spans WHERE trace_id = ? ORDER BY start_time — gives us the rows; the JSONL mapper is one Python function. Opik requires the Python SDK fetch loop with pagination, then the same mapper. Smaller delta on Laminar. Neither is a heavy lift but the SQL path is closer to "one query and a transform".

§10Interaction flow — what gets captured, end-to-end

The diagram below is the trace topology we want for one omp run. Every arrow is labelled with the wire format. run.id is the join key everywhere — it lives on the root span as an attribute, propagates to children via OTel context, and crosses the Bun/Python boundary via the traceparent environment variable. Laminar renders this as a transcript by default; the span tree is the alternate view.

Three things to notice in the diagram. First, run.id is the only identifier that crosses every boundary — it's a root-span attribute, propagated by OTel context for in-process children, by the traceparent env var when omp shells out to Hamilton, and by direct attribute when score.py attaches its 9 check results. Second, every long arrow is OTLP — meaning the entire run can be reconstructed from Laminar's trace store with no other backend. Third, the only non-OTLP edge is score.py reading the run-dir off the bind mount — the structural grader doesn't need traces, it grades artifacts on disk.

§11Five failure modes, five auto-alerts

These are the failure modes the 15_t17-smoke-1pt0-critic.html post-mortem identified as the next-to-fire. For each, the column on the right is the exact Laminar primitive (Signal, score attribute, or SQL query) that would trip on the first occurrence — not on the third, not after a human notices.

Failure modeSymptom in the runLaminar alert primitive
1. Token cliff Analyst spends 80% of context budget by sub-agent 4; critic gets a degraded prompt window and shortens its output. Today: invisible until reading critic.md and noticing it's thin. Signal: "analyst used >80% of its model's context window before the critic phase started". Backed by SUM(span.attr.gen_ai.usage.prompt_tokens) / model.context_window > 0.8 over the omp.run trace. Fires before critic invocation, not after.
2. Socket drop mid-critic The 6b73452 failure — TCP-level event during critic streaming, critic.md left at stub length, score 0.83. Today: caught only by score.py's check 5 failing. Signal: "critic span ended without OTLP end event". Detectable as span.status = UNSET + span.end_time IS NULL at trace-completion-time. Fires within seconds of the drop, not after the next score.py run.
3. Hallucinated claim citation A critic claim cites queries/q_07_xxx.sql that doesn't exist. score.py's check 6 sees that any .sql file exists; it does not cross-check citations. Custom span scorer: citations_resolved = all(c in run.queries for c in claim.cites). Attach to every critic claim span as score.citation_valid. SQL alert: WHERE score.citation_valid = 0. This is the D01 work, expressed in Laminar's scorer API.
4. Prompt drift analyst_prompt.md changes silently between runs. Run R7 and R8 look comparable in the score column; the analyst is actually being asked a different question. Span attribute: prompt.sha256 on every analyst.invoke. Signal: "prompt SHA differs from the previous run's prompt SHA". Trivially queryable via SQL; surfaces in the comparison view between any two runs.
5. JWT TTL squeeze Run completes in 9m 53s against a ~10-min Infisical universal-auth JWT. One slower run and the cred chain fails for a non-agent reason; score.py mis-attributes. Span attribute: auth.jwt_remaining_seconds set at root-span start. Signal: "run.duration_seconds > (jwt_remaining_seconds at start − 60)". Fires on completion of any run that came within 60s of the JWT cliff, regardless of whether it succeeded this time.
Why Signals beat per-failure scorers

Four of these five (1, 2, 4, 5) are not traditional eval problems — they're operational invariants we want enforced. Writing each as a custom LLM-judge scorer (the Opik idiom) means a model call per check per run. Writing each as a Signal (the Laminar idiom) means one NL description per check, evaluated deterministically against span attributes. The cost difference scales with run count. At 24 runs (D02 factorial) it's negligible. At the 500-run cadence we'll hit during reward-shaping, the Signal path is the only one that's free.

§12Deploy topology — the Tailnet box

The single docker-compose file that everything sits in. Laminar's 6 services + the harness + Hamilton + an Infisical edge. Secrets cross the trust boundary exactly once — at infisical run --silent. Traces cross the host boundary zero times — Laminar lives inside the same compose network.

docker run ━━ OTLP (trace data, default :4318) ━━ secrets path (one-shot at container spawn) ┄┄ artifact path (bind mount, host-readable post-run)

Three boundaries that matter on this diagram. (a) The trust boundary is at the infisical run call — secrets exist as env vars inside the compose network only for the lifetime of one omp process. (b) The Tailnet boundary is at the host: no container speaks Tailnet directly, Infisical access is mediated by the host-side signet → infisical-cli chain. (c) The artifact boundary is the .eval-out bind mount — score.py reads from disk, traces stay in Laminar's ClickHouse. The two stores aren't synchronised; the join key is run.id in both.

§13Four-week adoption sequence

Concrete commits, in order, against the insight-kit repo and the your-business/consumer-repo/deploy harness. Each week ends in a measurable invariant.

Week 1

Stand Laminar up alongside the harness

Pull docker-compose.yml from lmnr-ai/lmnr (the lightweight 6-service variant, no RabbitMQ). Add it to the deploy/eval/ compose alongside the existing harness service. Boot to http://localhost:5173. In omp/src/entry.ts, add programmatic NodeSDK init pointing OTLP at http://laminar:4318/v1/traces, with @opentelemetry/instrumentation-fs disabled. Wrap exactly one span — omp.run — with run.id as attribute. Invariant at end of week: one trace per ./eval-run.sh invocation shows up in the Laminar transcript view, with run.id queryable.

Week 2

Wire the analyst → sub-agent → critic → judge hierarchy

Add tracer.startActiveSpan() wrappers in analyst.ts, subagent.ts, critic.ts. Each opens a child span under omp.run; sub-agents spawn N siblings; critic and judge are siblings of the analyst. For Hamilton, set TRACEPARENT env when omp spawns the Python subprocess; in build_duckdb_views.py open a hamilton.dag span attached to the parent context. Add prompt.sha256 as a span attribute on every LLM invocation (axis 4 of §11). Invariant: one transcript per run shows the analyst, every sub-agent, critic, judge, and the Hamilton DAG nested correctly. Prompt SHA diffs visible in the comparison view.

Week 3

Custom scorers + Signals for the D01 + §11 invariants

Three custom Laminar scorers, one Python file each, registered on the critic.invoke span: claim_id_regex (matches ^MD-[DC]-G\d-\d{3}$), citation_valid (every cite in claims.jsonl resolves to a real file in queries/), length_prior (critic.md byte count within ±2σ of the 12,335-byte baseline). Five Laminar Signals, one for each row of §11 (token cliff, socket drop, hallucinated citation, prompt drift, JWT squeeze). score.py is modified to POST its 9 results (6 structural + 3 semantic) to Laminar via the API as span scores rather than only printing to stderr. Invariant: every run lands with both structural and semantic scores attached; any Signal firing is visible in the alerts pane within 30s of run completion.

Week 4

D02 factorial via Laminar Datasets + Harbor JSONL export

Create one Laminar Dataset of 24 items: 8 cells (AGENT × CHANNEL × MODEL) × 3 trials. Run the matrix via the eval CLI; the platform groups results by cell automatically. Read off drop-rate per CHANNEL, critic-length per MODEL, omp-exit rate per AGENT — the four marginals from 15_t17-smoke-1pt0-critic.html §4. For Harbor: a single SQL query against Laminar's query-engine produces (trace_id, span_id, parent_id, attributes['gen_ai.input.messages'], attributes['gen_ai.output.messages'], score.*); a 40-line Python transform converts this to Harbor's (state, action, observation, reward) trajectory JSONL. Invariant: the 24-cell matrix is repeatable as a one-line command; the JSONL export is one query + one transform; Harbor can consume the trajectory shape without further glue.

What's deliberately deferred

Langfuse stays in the "maybe later" bucket — strong trace viewer but eval primitives feel grafted on, and we don't want a second backend competing for the OTLP fan-out. Opik stays in the "if Laminar evals turn out too thin" bucket — the dataset/experiments idiom is genuinely nicer, but we'd be paying 11 services instead of 6 for a difference we can match with SQL. Phoenix is out (ELv2 + Bun JS errors per request). Dual-emit is out (operationally fragile, and we don't have a second use-case that justifies the cost).

Decision · revised 2026-05-25 post §9–§13

Ship Laminar. Single platform, six containers, transcript-first, SQL out to Harbor.

  1. Trace backbone: Laminar v0.1.45, Apache-2.0, lightweight 6-service compose alongside the harness. run.id as root-span attribute, OTel context for in-process children, traceparent env for the Bun → Hamilton hop.
  2. Agent UX + judge: Laminar's transcript view is the default render — exactly the reading mode omp's analyst → critic flow demands. Three custom scorers (claim_id regex, citation cross-validation, length-prior) cover D01; five Signals cover the §11 operational invariants.
  3. Datasets + Experiments: Laminar Datasets handle the D02 factorial (8 cells × 3 trials = 24 items); the SQL query interface answers the four marginals (drop rate per CHANNEL, critic length per MODEL, exit rate per AGENT, within-cell variance) without a comparison UI.
  4. Harbor path: one SQL query against Laminar's query-engine + a ~40-line Python transform produces Harbor's (state, action, observation, reward) trajectory JSONL. Smallest delta among the candidates.
  5. Bun tax: unchanged. Programmatic NodeSDK init at top of entry.ts, @opentelemetry/instrumentation-fs disabled, manual tracer.startActiveSpan() around analyst / sub-agent / critic / judge. Same tax we'd pay with Opik or Langfuse.

One-sentence verdict: Laminar wins on the two axes that scale with run count (deploy footprint at 6 containers vs Opik's 11; transcript UX that matches how we read agent runs) and ties on the axis that doesn't matter as much as it looks (built-in scorer library, because D01 is custom Python in any platform). Opik's stronger Datasets/Experiments idiom is real but recoverable via Laminar's SQL interface; Opik's 11-service compose is not recoverable.

If Laminar's eval ergonomics turn out worse than this analysis projects — say, the custom scorer API is more friction than Opik's — the fallback is to swap, not to dual-emit. Single-platform is a load-bearing simplification; dual-emit was the wrong answer in the earlier draft.
