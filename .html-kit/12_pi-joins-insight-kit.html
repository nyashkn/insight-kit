01  The 3-layer pi-harness

insight-kit stacks into three layers. Only the bottom one is "the real insight-kit" — the rest is swappable scaffolding around it.

L3 Orchestration loop pi sits here stateful · adaptive · self-improving

The coding-agent that generates claims. May be stateful, adaptive, even self-improving. This is the only layer allowed to change behaviour run-to-run — and the only layer pi touches.

L2 Compute spine pure · pinned-per-run

Pure, pinned-per-run functions. Hamilton or plain functions — a swappable driver. No side effects, no adaptivity within a run.

L1 Claim gate FROZEN · invariant V5 pure · runtime-agnostic Python

A pure, runtime-agnostic Python library at src/insight_kit/gate/. The four functions ik_claim_emit / ik_intervention_emit / ik_research_emit / ik_skill_use_emit are the only entry. Every record is pydantic-schema-validated, content-addressed (sha256) and immutable. Invariant V5 forbids it importing any orchestrator or Hamilton code.

"Freeze the gate, not the generator."

— insight-kit design council

Adaptive agents are allowed only as claim generators upstream of the frozen gate — never the gate, the compute spine, or the provenance record itself.

02  How a pi extension joins insight-kit

pi = @earendil-works/pi-coding-agent v0.75.4 — a TypeScript coding-agent framework (binary pi, installed via bun). A pi extension is a .pi/extensions/*.ts file exporting export default function (pi: ExtensionAPI) { … }. It joins insight-kit through three pi APIs.

pi.registerTool({ … })

Registers each of the 4 ik_*_emit gate calls as an LLM-facing tool. The tool's parameters field is a TypeBox schema — not Zod, not raw JSON Schema.

pi.exec("uv", ["run","python", … ])

The tool's execute() handler shells out to L1 (the Python gate) and returns the resulting RecordRef. This is constraint C4's "lang seam": L3 (TS) calls L1 (Python) via a uv run subprocess — the audit-engine run_check pattern.

pi.on("tool_call" / "tool_result", … )

Gate hooks. A tool_call handler can return { block: true, reason } to pre-flight-reject a claim-emitting tool before it runs; tool_result post-checks the emitted record.

parameters ← pydantic RecordSchema

The TypeBox parameters are generated from the pydantic RecordSchema via .model_json_schema() → JSON Schema → TypeBox (constraint C5: pydantic is the single schema source — no hand-kept twin).

pi agent (LLM) pi extension L1 Python gate RecordRef return pre-flight {block}

.pi/extensions/insight-kit.ts — extension shape

// .pi/extensions/insight-kit.ts
export default function (pi: ExtensionAPI) {
  pi.registerTool({
    name: "ik_claim_emit",
    label: "Emit claim",
    description: "Emit a typed claim record through the L1 gate",
    parameters: ClaimParamsTypeBox,      // generated from pydantic RecordSchema (C5)
    async execute(_id, params, signal, _u, ctx) {
      const r = await pi.exec("uv",
        ["run","python","-m","insight_kit.gate.cli","claim"],
        { signal, cwd: ctx.cwd, timeout: 30_000 });
      if (r.code !== 0) throw new Error(r.stderr);
      return { content: [{ type: "text", text: r.stdout }] };
    },
  });
  pi.on("tool_call", (e) => { /* gate pre-flight → {block,reason} */ });
}

03  The modularity answer

The question: does the design let L3 be swapped — pi today, or Claude Code SDK, or agent-deck (agent-team-orchestration)?

Answer: yes.

L1 is a pure, runtime-agnostic library whose entire surface is 4 functions, exposed behind a subprocess CLI seam. Any orchestrator that can (a) spawn a subprocess and (b) render tool parameters from a JSON Schema can drive L1.

Three orchestrators around one frozen gate

Each adapter is a thin glue layer over the shared CLI + schema seam. The MCP route is even simpler — MCP tool inputSchema takes JSON Schema directly, so the TypeBox conversion step is skipped entirely.

Two things split cleanly:

Build once · orchestrator-agnostic

Shared core

The L1 subprocess CLI contract, plus the pydantic → JSON-Schema export. Built once, drives every orchestrator. This is the part T18 actually builds.

Per-orchestrator · thin

Thin adapter

pi's registerTool glue / the MCP server wrapper / the agent-deck tool-def. Small, isolated, swappable — deferred glue, one per orchestrator.

This is exactly the "T18 = build the core, defer the glue" split — and that split is the proof of modularity.

04  Proposed Signet-style monorepo structure

Signet (Signet-AI/signetai) splits its repo into platform/ (frozen core engine), libs/ (shared SDK + a connector-base contract), surfaces/ (human-facing I/O), integrations/ (one isolated package per AI-harness connector), and deploy/ (packaging, zero business logic). It is a Turborepo monorepo; dependencies flow inward only.

Proposed insight-kit mapping

insight-kit/

    harness/       eval harness (T17) — Python
  libs/

Your own instinct — "an agents/code-agents folder with pi as its own package, Evidence as a separate package" — is exactly Signet's integrations/ + surfaces/ split. Dependency flow: deploy → surfaces + integrations → libs/gate-cli → platform/gate. The gate never imports outward — that is what keeps L3 swappable.

Why the lang seam is a subprocess and not an in-process FFIoptional depth

L3 is TypeScript; L1 is Python. An in-process bridge (PyO3, a Python embed, a long-lived RPC daemon) would couple the two runtimes' lifecycles and versions. The uv run python -m insight_kit.gate.cli subprocess instead gives a clean process boundary: each claim emit is an isolated invocation with its own pinned env, stdout carries the RecordRef as JSON, and a non-zero exit code surfaces as a thrown error. This is the same run_check pattern the audit engine already uses — constraint C4 — so the orchestrator never needs a Python runtime in-process, only the ability to spawn one. It is also what makes the seam orchestrator-agnostic: any L3 that can spawn a subprocess can drive L1, no shared memory model required.
