The cache, on a real pipeline.

Hamilton's cache is the structural answer to the analyst's exploratory loop: 5 throwaway .py + 1 final annotated module. When the analyst tweaks one node, only that node and its descendants recompute. Everything upstream is a cache hit. This page shows what that looks like on a five-node growth_insights pipeline — first run, edit-cohort-filter, edit-input, edit-config — with concrete fingerprints.

extract_shopify_orders→ join_meta_ads→ cohort_filter→ build_initiatives→ evidence_view

§1The fingerprint

A Hamilton cache entry is keyed by a fingerprint. The fingerprint is the SHA-256 of three things stitched together:

fingerprint(node)
sha(source-code body of the function) ⊕ sha(fingerprints of every upstream node) ⊕ sha(relevant Driver config values)

Three consequences flow from this definition:

  • Edit code in a node → its code chunk changes → fingerprint changes → it recomputes. Every descendant's input chunk also changes → descendants recompute. Ancestors are untouched.
  • Edit raw input on disk → the source node (the one that reads the file) sees a new input chunk → recomputes → cascade.
  • Edit a config value referenced via @config.when or a parameter resolved from Driver.with_config(...) → only nodes whose config chunk includes that key recompute.
Source of truth
Hamilton's tutorial materials live at /tmp/hamilton/examples/caching/ — tutorial.ipynb, in_memory_tutorial.ipynb, materializer_tutorial.ipynb. The HamiltonCacheAdapter exposes four behaviours: DEFAULT (use cache), RECOMPUTE (force re-run, write to cache), DISABLE (skip cache entirely), IGNORE (read cache, don't write). insight-kit's recommended setting during exploration is RECOMPUTE; for promoted modules, DEFAULT.

§2The pipeline we'll trace

Five nodes, taken from a plausible Hamilton port of the existing analyses/g1_spend_reallocation work. The shape is real (the inputs exist under data/agent_runs/2026-04-23_2218_human_shopify_orders_bulk/output/orders.parquet and data/agent_runs/2026-04-24_0413_w1_adset_targeting_meta_metadata/output/); the module itself is illustrative. 

  # analyses/spend_reallocation.py
  import pandas as pd
  from hamilton.function_modifiers import tag, config

  def extract_shopify_orders(orders_parquet_path: str) -> pd.DataFrame:
      return pd.read_parquet(orders_parquet_path)

  def join_meta_ads(
      extract_shopify_orders: pd.DataFrame,
      meta_metadata_parquet: str,
  ) -> pd.DataFrame:
      ads = pd.read_parquet(meta_metadata_parquet)
      return extract_shopify_orders.merge(
          ads, left_on="utm_campaign", right_on="campaign_name", how="left")

  def cohort_filter(
      join_meta_ads: pd.DataFrame,
      min_purchase_kes: int,         # config-driven
  ) -> pd.DataFrame:
      return join_meta_ads[join_meta_ads.purchase_value_kes >= min_purchase_kes]

  @tag(emit="metric", claim_tier="derived",
       claim_id="MD-D-008")
  def build_initiatives(
      cohort_filter: pd.DataFrame,
  ) -> pd.DataFrame:
      grouped = cohort_filter.groupby("age_gender_segment")\
                             .agg(roas=("revenue_kes","sum"),
                                  spend=("spend_kes","sum"))
      grouped["roas_ratio"] = grouped.roas / grouped.spend
      return grouped.reset_index()

  @tag(emit="viz", claim_tier="viz", claim_id="MD-V-002")
  def evidence_view(
      build_initiatives: pd.DataFrame,
  ) -> pd.DataFrame:
      return build_initiatives.sort_values("roas_ratio", ascending=False)\
                              .head(20)

§3Scenario A — first run, cold cache

A

Every node executes and caches.

Nothing in the cache yet. The Driver walks the DAG topologically and runs each node. After each node returns, the cache adapter writes a row keyed by the fingerprint, value = the result (serialized via the materializer).

5 / 5 nodes executed. Wall time = sum of compute. Claims MD-D-008 and MD-V-002 emitted via InsightKitHook. manifest.json records 5 OutputRecords (one per node) plus the input parquet shas.

§4Scenario B — edit cohort_filter

B

Analyst tightens the cohort threshold logic. Only it + downstream recompute.

The analyst changes cohort_filter's body to also drop rows where purchase_value_kes exceeds the 99th percentile (truncate outliers). They re-run.

3 / 5 nodes executed. 2 cache hits. Shopify parquet was not re-read. Meta join was not recomputed. Two new claim emissions (MD-D-008, MD-V-002) with supersedes back-references to their prior IDs. This is the loop that today eats 4 throwaway scripts.

§5Scenario C — input parquet refreshed

C

Upstream ingest re-ran. Everything cascades.

The Shopify ingest worker re-pulled overnight; orders.parquet now has a different sha. The analyst re-runs without changing any code. extract_shopify_orders reads the file and gets a new dataframe — its downstream nodes' input chunks all change.

5 / 5 nodes executed. No cache hits — but the cache stays useful for the next edit. This is the worst case: it costs the same as Scenario A. The win is that the analyst didn't have to think about which downstream views to refresh — Hamilton walked the descendants for them.

§6Scenario D — config flip only

D

Threshold change: min_purchase_kes from 50 → 200.

The analyst is sweeping the threshold to see which level surfaces the strongest signal. They run the Driver with dr.with_config(min_purchase_kes=200).build(). Only nodes that read this config key recompute. Everything else hits cache.

Nodecode chunkinput chunkconfig chunkState
extract_shopify_orders7a3f…b210— (root)e1c0…HIT
join_meta_ads9b14…d8e2⊕ shopify_fpe1c0…HIT

3 / 5 nodes executed. extract_shopify_orders and join_meta_ads don't reference min_purchase_kes, so their config chunk is unaffected and they hit cache. Run a 6-value sweep (50, 100, 200, 500, 1000, 2000) and you pay parquet-read + join cost once; each threshold then costs only the three downstream nodes.

§7Why this matters for insight-kit's iteration shape

today (no cache)

5 throwaway .py + 1 final module

The pattern documented at nairomarket/growth_insights/CLAUDE.md — analyst spikes five exploratory scripts, each re-reads the same parquet, each computes the same join, each writes its own claims. Sequencing is bash, sha tracking is manual, "this run is broken, let me edit and re-run" means re-running everything from disk.

after Hamilton cache

One module, N config sweeps, free

The five spikes collapse into one module. The "swap the cohort threshold" iteration costs only the changed branch — Scenario D. The "fix a typo in the join" iteration costs only the join + everything downstream — Scenario B. The "ingest refreshed overnight" iteration is a full recompute — Scenario C — but the analyst doesn't have to remember to invalidate the views.

Tie-back
Cache invalidation = claim invalidation. When cohort_filter recomputes, build_initiatives re-emits MD-D-008 with a supersedes edge pointing at the prior run's claim of the same ID. The old MD-D-008 is preserved on disk (older run dir) but Layer-B's uniqueness rule is satisfied by the supersedes chain. The Evidence.dev claims_manifest view exposes both rows; the page renders the latest by default and the timeline on hover.

§8Operational notes

  • Cache backend. Hamilton ships an in-memory cache by default; for persistence pair with the h_diskcache plugin or a custom adapter that writes to .insight-kit/cache/. The fingerprint becomes the filename. See result store options.
  • Pinning. @cache(behavior="recompute") on a node forces a fresh run regardless of cache state — useful for nodes that read live APIs (Meta, Shopify) where the input isn't deterministic.
  • Eviction. No automatic eviction. The cache is content-addressed and append-only; clean up with a CLI sweep keyed by mtime or run-dir purge.
  • Cache vs manifest. The cache stores compute results. The manifest stores provenance. They are not the same artifact — even with a cache hit, insight-kit's hook still emits OutputRecord + claim into manifest.json + claims.jsonl for the new run. Cache speed up; manifest preserves audit.
  • Notebook bridge. The same cache works inside a Jupyter session. An analyst iterating in a notebook with dr.execute([…]) gets the same incremental behaviour as the CLI — that's what makes "5 exploratory .py" obsolete.

§9What this page deliberately does not cover

  • Distributed cache (Ray, Dask). Same mechanics, different store. Read /tmp/hamilton/examples/caching/ notebooks.
  • Pandera-typed cache keys. Pairs naturally with @check_output; out of scope here.
  • Cross-run cache sharing across analysts. Requires shared backend (S3, Postgres); operational concern, not a mechanism question.
  • Manual cache invalidation CLI. The integration plan owes one but doesn't ship it yet; planned as ik cache purge --before <date>.

Glossary · this page

Click any dotted term to jump here.
Fingerprint
SHA-256 of three components stitched together: the code hash (function body), the input hash (fingerprints of every upstream node), and the config hash (relevant Driver config values). Uniquely identifies the expected output of a node given its current state.
Code hash
The SHA-256 of a Hamilton node's Python function body. Changing any character in the function — even whitespace — produces a new code hash, invalidating the cache for that node and all descendants.
Input hash
The XOR/concatenation of the fingerprints of every upstream node that feeds into a given node. If any ancestor recomputes (changing its fingerprint), the input hash of all downstream nodes changes too.
Config hash
The SHA-256 of the Driver config values referenced by a node (e.g. min_purchase_kes). Only nodes that actually consume a config key are affected when that key changes.
HamiltonCacheAdapter
The Hamilton plugin (from hamilton.plugins.h_cache) that intercepts node execution. Before running a node it checks whether a cached result exists for the current fingerprint; after running it writes the result to the store.
Cache behavior
One of four modes controlling how the adapter handles a node: DEFAULT — use cache if hit; RECOMPUTE — force re-run, then write; DISABLE — skip cache entirely; IGNORE — read cache but never write. Recommended: RECOMPUTE during exploration, DEFAULT for promoted modules.
Cache hit
When the current fingerprint of a node matches a stored fingerprint, the cached result is returned and the function body is not executed. Shown as HIT in the scenario tables.
Cache miss
When no stored entry matches the current fingerprint — either the cache is cold (first run) or the fingerprint changed. The node executes and the result is written to the store.
Node
A Python function in a Hamilton module. Each function is a node in the DAG; its name is its output column name. Nodes declare dependencies through parameter names matching other node names.
Driver.execute()
The Hamilton entrypoint that walks the DAG topologically and executes (or cache-hits) each node needed to produce the requested outputs. Called as dr.execute([…], inputs={…}).
@config.when
Hamilton function modifier that activates a node only when a Driver config value matches. Affects the config chunk of the fingerprint — changing the referenced config key invalidates only the nodes decorated with matching @config.when conditions.
Materializer
The serializer/deserializer the cache adapter uses to store and restore node results. Common choices: parquet for DataFrames, pickle for arbitrary objects, json for small dicts. Configured per-node or globally on the adapter.
Result store
The persistence backend for cached results. Options include in-memory (default, non-persistent), h_diskcache (file-based), SQLite, or Redis. The fingerprint becomes the lookup key; the result is the serialized value.
Claim invalidation
When a node recomputes, its downstream claim emissions (via @tag(claim_id=…)) produce new claims with a supersedes back-reference to the prior claim of the same ID. Old claims are preserved on disk; the manifest renders the latest by default.
Idempotency
A property of the cache: running the same inputs + code + config multiple times always produces the same fingerprint and thus the same cached result. No side effects accumulate from repeated runs.
extract_shopify_orders
The root node of the example pipeline. Reads orders.parquet from disk; its fingerprint's input chunk reflects the file's content hash. A new ingest run that updates the parquet cascades a full recompute through the DAG.
Upstream / downstream
Upstream nodes are dependencies (they appear as parameters in a function). Downstream nodes depend on the output of a given node. A fingerprint change always cascades downstream only — ancestors are never affected by a descendant's change.
