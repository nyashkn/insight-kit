DataFrame stack — h_dlt · h_polars · h_narwhals

Three Hamilton plugins that own the data lifecycle before the analyst writes a transform. Together: source connector → compute engine → engine-agnostic API. Each plugs into a different seam without overlap.

API / SaaS→ h_dlt→ parquet / duckdb→ h_polars or h_narwhals→ Hamilton node→ Pandera→ Claim

§0Where the three sit

Three plugins, three seams. h_dlt handles arrival. h_polars / h_narwhals handle compute engine choice. Decoupled — adopt any combination.

§1h_dlt

dlt source · bridge

Treat dlt sources as Hamilton nodes — useful if you formalise the ingest layer.

Pain today (grounded)

scripts/f7_shopify_customer_pull.py (~60 LOC visible) hand-rolls GraphQL bulk-op + poll loop + JSONL download. Same pattern in f7_shopify_poll_and_fetch.py, f7_meta_audience_upload.py, plus the bulk-op scripts feeding 2026-04-23_*_shopify_products_bulk/ + 2026-04-24_*_meta_metadata/ runs.

Each run is a full snapshot — no cursor. Day-2 re-downloads all customers when only 3 changed. No schema evolution. Token in os.environ.

§2h_polars

polars eager + lazy

If your viz / compute layer is polars-first, no conversion penalty.

Pain today (grounded)

Compute layer is DuckDB-SQL-heavy — scripts/build_duckdb_views.py + Evidence ```sql blocks (e.g. reports/pages/profitability.md SKU P&L over 26 months). Python compute happens in scattered notebooks w/ implicit pandas conversion.

No measured perf problem yet. The win is forward-looking: once cohort-window joins exceed ~5M rows, pandas group-by stalls; polars finishes in seconds.

from hamilton.plugins.h_polars import PolarsImplementation
import polars as pl

def cohort_filter(
    orders: pl.LazyFrame, cutoff: dt.date,
) -> pl.LazyFrame:
    return (
        orders
        .filter(pl.col("placed_at") >= cutoff)
        .group_by("customer_id")
        .agg(pl.col("order_value").sum().alias("ltv"))
    )

Skip for now. Adopt when a node's group-by takes >30s on real data or when memory pressure on cohort joins becomes a complaint. Premature today — no measured win.

§3h_narwhals

DataFrame-agnostic API

Write nodes once, run against pandas or polars.

Why it exists

Narwhals is a thin compatibility layer over pandas/polars/modin/cudf/pyarrow. One node body, swap engine at Driver.Builder() time. Useful when you don't know which engine wins, or when analysts work in pandas + production runs polars.

For growth_insights: keeps analysts in pandas (notebooks) while letting prod ingest go polars without rewriting cohort logic.

import narwhals as nw
from narwhals.typing import IntoDataFrame

def cohort_filter(
    orders: IntoDataFrame, cutoff: dt.date,
) -> IntoDataFrame:
    df = nw.from_native(orders)
    out = (
        df.filter(nw.col("placed_at") >= cutoff)
          .group_by("customer_id")
          .agg(nw.col("order_value").sum().alias("ltv"))
    )
    return nw.to_native(out)   # pandas in → pandas out
Trade-offDetail
Pro · engine portabilityanalyst writes once, prod picks engine at build time
Pro · no engine lock-inswap pandas→polars w/o rewriting transform code
Con · API surface smallernarwhals exposes intersection of pandas+polars · advanced features (polars lazy window, pandas pivot_table) gated

When to pick

Adopt only if analysts will keep notebooks in pandas while prod pipelines run polars. If team commits to one engine, skip narwhals and use that engine directly. Avoid as default — premature abstraction.

How they compose

  1. h_dlt writes shopify.orders to duckdb · auto-cursor on updatedAt
  2. downstream Hamilton node reads parquet via h_polars.PolarsImplementation → LazyFrame
  3. transform written in narwhals API → engine swappable at Driver.Builder()
  4. Pandera @check_output(schema=…) validates the materialized frame
  5. Run emits Claim · Layer A/B/C runs · Evidence renders

Each step owned by exactly one tool. No overlap. Cache fingerprint flows the whole chain.

Adopt h_dlt now. Defer h_polars. Skip h_narwhals unless dual-engine.

Glossary

dlt
data load tool. Python lib for incremental ingest w/ auto state cursor, schema evolution, idempotent merge, multiple destinations (parquet/duckdb/postgres). Community sources for Shopify, Meta, GA4, Brevo.
Polars
Rust-backed columnar DataFrame lib. Arrow-native. Eager + lazy APIs. Multithread by default. 10×–100× pandas on group-by/join at >1M rows.
Narwhals
DataFrame-agnostic API layer. Thin shim over pandas/polars/modin/cudf. Write transform once, swap engine at runtime. Exposes intersection of supported APIs.
Cursor (incremental)
State value (e.g. updatedAt) that dlt persists between runs. Next run filters source to rows > last cursor. Enables idempotent merge.
write_disposition
dlt parameter. replace = full snapshot. append = add only. merge = upsert by primary key. Use merge for Shopify customers/orders.
LazyFrame
Polars deferred-execution frame. Build query plan, optimize, materialize once at .collect(). Hamilton fingerprint sees same hash regardless of when materialization happens.
@source_to_node
Hamilton h_dlt decorator. Wraps a dlt source as a Hamilton node. Node returns dict of DataFrames (one per resource). Gets fingerprint cache + lineage automatically.
Schema drift
Upstream API changes column name/type. Today: silent KeyError mid-pipeline. With dlt: detected + auto-evolved + drift event emitted. Pair w/ Pandera for loud failure.
dlt.secrets
dlt's credential resolution. Pluggable to env, vault, Signet Secrets. Beats os.environ["TOKEN"] — no token in code, no env leak risk.
Engine swap
Narwhals/h_narwhals property. Same node body runs against pandas, polars, modin, cudf depending on Driver.Builder() config. Useful for notebook (pandas) vs prod (polars) parity.
