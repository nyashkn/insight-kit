Agent team orchestration

A goal-run today is a manual relay of single-agent sessions. This page proposes a conductor that thinks deep about the goal once, then fans out analyst+data_eng pairs in parallel — each pair welded as one unit — gated by a binary published / draft tier, wired through an /agent-deck profile, with a three-namespace Signet memory model: role / goal / run.

run conductor thinks → N pairs fan out → bundles → critic gates → renderer composes

§0What's wrong with orchestration today

Roles exist (.agents/agents/{analyst,critic,renderer,data-engineer,annotator}/AGENT.md). Bootstrap exists. But the orchestration layer — how roles compose into a goal-run — is implicit. Eight failure modes:

O-1 · implicit DAG
Pipeline order lives in runner code + human head. No shared task graph agents read. Reordering = rewriting runner.
O-2 · no mid-flight comms
Renderer reads narrative.md cold. Can't ask analyst "MER full or partial month?" Re-reads, guesses, hallucinates.
O-3 · critic async gate
Found-then-fix loop. Critic flags after build done → human reruns analyst → 80% of context rediscovered.
O-4 · data_eng reactive
Analyst hits missing feature → run halts → human PRs feature → resume. Should resolve inline.
O-5 · no parallelism
3 claims = 3 serial sessions. ~30 min. Should be ~10 min parallel.
O-6 · context re-read
4 roles each reload goal context cold. ~120k tokens of duplicate reads per run.
O-7 · no correlation
Run-id exists; agent-instance-id doesn't. "Which analyst said this?" untraceable on parallel builds.
O-8 · annotator bolt-on
Runs post-hoc as a sweep. Could be inline during render.

The fix is not "more agents." It is a composition layer: a shared task list, peer messaging, and a conductor that owns the goal interpretation so the workers don't each re-derive it.

§1Revised shape — conductor + paired fan-out

Earlier draft had analyst and data_eng as separate team members — wrong cell boundary. It forces a cross-team message for every feature request. The pair is the unit. Inside a pair, data_eng services analyst's feature needs at zero coordination cost. Pairs fan out; roles don't.

§2Conductor — think deep before fan-out

The conductor is not a dispatcher. It is the one session that understands the goal so the workers never have to re-derive it. This is the System-2-once, System-1-many pattern: pay the deep-reasoning cost a single time.

Deliberation phase

# conductor session — runs before any pair spawns
1. read goal_spec.md (immutable goal artifact in run-dir)
2. recall goal:{slug} memory  → prior runs of similar goals
3. query claims_registry     → prior claims worth referencing
4. draft claim graph:
     - which claims this goal needs
     - which features each claim consumes
     - which features missing  → data_eng workload
     - which prior claims to link (supersession / baseline / intervention)
5. decide N (pair count):
     claims sharing >50% features  → SAME pair  (cache reuse)
     else                          → SPLIT pair  (parallelism)
6. write goal_plan.md  → run-dir
7. post tasks to shared task list, one per claim + one compose task
8. spawn pairs

Cost: one opus session, ~30–50k tokens of reasoning. It saves multiples of that downstream — each pair reads goal_plan.md instead of re-interpreting goal_spec.md from scratch. Kills failure mode O-6.

why a thinking conductor, not a script
A scripted decomposer splits by naive rule ("one claim per metric"). A reasoning conductor sees that "March cash" and "March MER" share the same monthly feature set → one pair, one cache warm-up, half the cost. It also catches goal-level contradictions before fan-out — the cross-page reconciliation that today only surfaces in a Socrates audit after render.

§3The pair — analyst writes code, data_eng serves inline

Two corrections to the earlier draft: (1) the analyst's primary output is Python, not prose — Hamilton node defs + claim build, extracting from .pq via h_polars; narrative.md is downstream of the code. (2) data_eng lives inside the pair, not as a team peer.

analyst · opus

Authors claims as code

writes build.pyh_polars on .pq

Reads goal_plan.md. Writes claims/{id}/build.py — a Hamilton node that pulls from .pq files, computes via catalog features, emits the typed Claim. Then narrative.md interpreting it. Code first, prose second.

data_eng · sonnet

Serves features inline

features/*.pyh_dlt sources

Listens on the pair channel. Analyst requests a missing feature → data_eng writes the node, runs the naming lint, replies done · sha256. Analyst never halts. Owns source freshness via h_dlt cursors.

pair channel

Zero-coordination comms

run:{id}:pair-Kpeer msg

Both pair members read/write one shared scratch namespace. Feature request → response → resume, all within the pair. No conductor round-trip. Other pairs never see this traffic.

Analyst output — code, then prose

§4Goal tier — binary, not three

Earlier draft split audience into three. Wrong. Founder and board share the same enforcement kind — low tolerance, blocks render. Internal-shared and draft share the other kind — allow with badges. The real axis is binary: will this be shared, or not.

TierTriggerOrchestrationEnforcement
publishedfrontmatter status: ship OR audience ∈ {board, founder, internal-shared}Full team — conductor + N pairs + critic + renderer. Vision-critic on. Staleness watcher armed.Block render on unresolved critique or >1% drift.
draftdefault — anything not yet marked to shipSingle agent with tool access. No team spawn. Critic optional.None. Badges only.

Promotion draft → published re-runs the goal as a team. Cheap, because the bundles already exist and the conductor's prior plan is usually reusable — the re-run is mostly critic + renderer.

why binary beats three tiers
Three tiers means three code paths, three policy tables, three test matrices — for a distinction (founder vs board) that never changes behaviour. Binary collapses it. The drift threshold can still vary by audience inside the published tier (a number in a config), but the orchestration is one of two shapes. Config varies; architecture doesn't.

§5/agent-deck integration

Don't hand-roll a session manager. /agent-deck already does session lifecycle, MCP attach, groups, worktree isolation. Add an insight-kit orchestration profile on top.

verified · /agent-deck mapped 2026-05-21
Two findings shift the design. (1) agent-deck profiles are not declarative TOML — they are CLI-spawned runtime namespaces (agent-deck profile create). (2) agent-deck already has a native [conductor] concept — our conductor maps straight onto it. And the Claude teams flag CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 is already set in ~/.claude/settings.json:18 — no enablement work.

Bring-up — CLI, not config file

# profiles are runtime namespaces, created + populated via CLI
agent-deck profile create insight-kit

# conductor = native agent-deck concept ([conductor] section, on by default)
agent-deck -p insight-kit conductor setup orchestrator \
    -agent claude -description "insight-kit goal-run orchestrator"

# worker sessions, grouped for run-correlation (kills O-7)
agent-deck -p insight-kit group create run-{run_id}
agent-deck -p insight-kit launch ~/insight-kit \
    -t "pair-1-analyst" -g run-{run_id} --worktree run/{run_id}/pair-1
agent-deck -p insight-kit session set-parent pair-1-analyst orchestrator

# MCP attach is PER-SESSION — no profile inheritance (blocker B1)
agent-deck -p insight-kit mcp attach pair-1-analyst signet
agent-deck -p insight-kit mcp attach pair-1-analyst hamilton

# ik wrapper hides the loop:  ik agents goal-run --goal=<slug>

Blockers — confirmed, with workarounds

#BlockerWorkaround
B1No profile-level MCP scope — MCPs attach per-session, not inheritedik agents goal-run wrapper loops mcp attach over every spawned session. Mechanical, ~6 lines.
B2Conductor supports the claude agent only (no Codex)Non-issue — all five roles are Claude. Model diversity (opus vs sonnet) is set per session, not per agent-type.
B3Bridge daemon messaging is async + heartbeat-polled — "slow-loop, not real-time"Refute loop tolerates seconds of latency (a critique is not a hot path). Set heartbeat_enabled + a low poll interval for the run's duration. Don't expect sub-second.
B4session set-parent routing is unidirectional — conductor reads workers; worker→parent needs explicit session sendPair channel uses the Signet run:{id}:pair-K namespace (§6), not agent-deck routing. agent-deck routing reserved for conductor↔worker lifecycle only.

Net: agent-deck covers conductor, worktrees, groups, parent-child — the spine. Peer messaging within a pair routes through Signet's namespace instead of the bridge daemon, which sidesteps B3 + B4. No agent-deck source changes needed; the ik wrapper absorbs B1.

§6Signet memory — three-namespace model

Agents need memory. The question is scope. One shared pool → memory wars. Per-agent-instance pools → no cross-run learning. The answer: three concentric namespaces — role, goal, run — with role-isolated writes and union reads.

role:{analyst | data_eng | critic | renderer | conductor}
Durable. Cross-goal, cross-run. Lessons that belong to the craft of a role — "partial-month MER is a bug class", "naming convention is measure_agg_grain_dim", critic failure recipes. Every agent of that role, in any future run, reads this.
lifetime: permanent · writer: that role only · cap ~200 entries, evict by recency × feedback
goal:{slug}
Durable. Per-goal, cross-run. "Founder weekly cash" learned across its last 3 runs — canonical decomposition, recurring claim IDs, known data quirks for this goal. Lets the conductor warm-start.
lifetime: permanent · writer: conductor · readers: all roles
run:{run_id} · sub: run:{run_id}:pair-K
Ephemeral. One run only. goal_plan.md decisions, mid-run choices, claim drafts. The pair-K sub-namespace is the pair's private scratch — analyst posts a feature request, data_eng posts the response.
lifetime: TTL 30 days then burn · writers: all (run) / pair members (pair-K)

Access rules

self-tuning corpus
Signet already exposes memory_feedback. Score each memory per recall (helpful / unused / harmful). Low-score role: entries evict first when the 200-cap is hit. The corpus tunes itself per role — analyst memory converges on what analysts actually reuse, not what seemed useful when written.

§8Council · orchestration deliberation

Lao Tzu · emergence

Don't over-architect. Ship conductor + 1 pair first. Watch what the run actually needs. Adding pairs is cheap; unwinding a wrong abstraction is not.

Munger · multi-model

Paired analyst+data_eng is the cell pattern — Toyota work cells, XP pair-programming. Proven. But cells need a deliberate cross-cell sync or they diverge. That's the conductor's standing job, not an afterthought.

Machiavelli · power

Who holds veto? Critic must refute after a pair converges, never during — mid-build veto = paralysis. data_eng scope-vetoes escalate to conductor. One arbiter, clear order, or the team deadlocks.

Sun Tzu · strategy

Fan-out wins only when work parallelizes cleanly. One claim → one pair, no fan. The disjoint-feature threshold is the terrain read — commit forces only where ground is divided.

Kahneman · cognition

Conductor "thinks deep" = System 2, paid once. Pairs run System 1 plus a bounded refute loop. Cap critique rounds at 3 — past that, judgement is noise; escalate or downgrade tier.

Taleb · tail risk

The run namespace is the sacrifice layer — burn it after close, it never poisons durables. Worktree-per-pair contains a bad build to one tree. Both bound the blast radius. Keep them.

Synthesis · verdict

Adopt conductor + paired fan-out, but stage it. Phase 1 = protocol only (shared task list + peer-msg, single agent self-messaging) — proves the wiring with no spawn cost. Phase 2 = 3-agent internal team. Phase 3 = full 5 w/ vision critic. Gate fan-out on disjoint features and goal tier. Cap critique rounds at 3. Conductor is the sole cross-namespace writer and the sole compaction caller. Memory: three namespaces, role-write-isolated, union-read.

Glossary

Conductor
Opus session that interprets the goal once, drafts the claim graph, decides pair count, writes goal_plan.md, then spawns pairs. Owns run lifecycle + compaction. Not a dispatcher — a reasoner.
Pair
analyst (opus) + data_eng (sonnet) welded as one fan-out unit. data_eng services analyst's feature requests on a private channel — zero cross-team coordination.
Goal tier
Binary: published (will be shared — full team, vision critic, blocks render) vs draft (single agent, badges only). Replaces the earlier 3-tier split.
/agent-deck
Terminal session manager — profiles, MCP attach, groups, worktree isolation, lifecycle hooks. Orchestration runs as a named agent-deck profile.
Agent teams
Claude Code feature: shared task list + inter-agent messaging. Enabled per profile via a teams flag. Lets pairs message peer-to-peer.
Signet memory
Persistent agent memory. Here scoped into three namespaces — role (durable craft knowledge), goal (durable per-goal canon), run (ephemeral per-run state).
role: namespace
Durable, cross-goal. The craft knowledge of a role. Only that role writes it. Capped ~200 entries, evicted by recency × feedback score.
goal: namespace
Durable, per-goal, cross-run. Canonical decomposition + recurring claim IDs. Conductor-write-only. Lets the conductor warm-start.
run: namespace
Ephemeral, one run. goal_plan.md decisions + the pair-K private scratch channel. TTL 30 days then burned.
Claim bundle
From E: claims/{id}/ dir holding claim.json + narrative.md + chart spec/png + data snapshot. The artifact the team collaborates around.
Worktree session
agent-deck spawns each pair in an isolated git worktree → claim-file edits never collide across parallel pairs.
