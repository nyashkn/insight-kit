apache/hamilton · v1.x · incubating (Apache 2.0)

Hamilton, in one read.

A micro-framework that turns Python functions into a typed DAG by matching parameter names to function names. No explicit edges. No DSL. A Driver picks an executor (sync / multi-proc / Ray / Dask / Spark), runs the graph, and fires lifecycle hooks at every stage — which is exactly the seam insight-kit needs to bolt provenance onto compute without rewriting the user's code.

funcs = nodes· @tag· Driver· lifecycle hooks· @check_output· cache· materializers

§1The one mental model

You write a module of plain Python functions. The function's name is the node's name. The function's typed parameters are the node's upstream dependencies — Hamilton resolves them by name match against other functions in the module. That's it. The FunctionGraph is the module. 

  # analyses/funnel.py
  import pandas as pd

  def zoho_raw(zoho_url: str) -> pd.DataFrame:
      return pd.read_parquet(zoho_url)

  def zoho_silver(zoho_raw: pd.DataFrame) -> pd.DataFrame:
      return zoho_raw.dropna(subset=["stage"])

  def fnl_count_by_stage(zoho_silver: pd.DataFrame) -> pd.DataFrame:
      return zoho_silver.groupby("stage").size().reset_index(name="n")

  # Driver:
  from hamilton import driver
  import analyses.funnel as funnel
  dr = driver.Builder().with_modules(funnel).build()
  result = dr.execute(["fnl_count_by_stage"], inputs={"zoho_url": "..."})

No @task. No graph.add_edge(). No YAML. The DAG is the call graph of pure functions. Reading the module top-to-bottom reads the pipeline.

§2Decorators worth knowing — grouped

Metadata

@tagAttach arbitrary KV metadata to a node (owner, source, PII, emit-mode, claim_tier). Hooks read these to dispatch.
@schemaDeclare output schema (pandera, polars, ibis).

Parameterisation (fan-out)

@parameterizeExpand one function into N nodes by parameter sweep. This is the council pattern.
@parameterize_sourcesFan-in: same function reads from N different upstreams.
@extract_columnsUnpack a multi-column DataFrame into one node per column.
@extract_fieldsUnpack a dict/dataclass field-by-field into sibling nodes.

Higher-order composition

@subdagEmbed a sub-graph. This is the critic-of-claim pattern.
@parameterized_subdagSweep over a sub-graph (multiple critics × multiple angles).
@pipe / @pipe_input / @pipe_outputFunctional composition (Unix-pipe style).
@config.when(env="local")Conditionally include a node based on Driver config. Notebook vs prod toggling.

I/O (materialisers)

@save_to.parquetAttach a node that persists upstream result to parquet. Path, partitioning, format.
@load_from.parquetAttach a node that loads from parquet.
@datasaver / @dataloaderCustom I/O adapter registry (subclass DataSaver → ride @save_to.<your-format>).

Data quality

@check_output(validators=[...])Run validators on the result. Built-ins: range, type, pandera schema. importance="error" raises; "warning" logs.
@check_output_customCustom validator function.

Caching

@cache(behavior=...)Per-node override: DEFAULT (hit skips), RECOMPUTE, DISABLE, IGNORE.

§3Driver lifecycle

dr = (
  driver.Builder()
    .with_modules(analyses.funnel, analyses.brevo)   # the DAG sources
    .with_config({"env": "local"})                    # @config.when toggling
    .with_adapters(InsightKitHook(run),               # <-- insight-kit plugs here
                   HamiltonCacheAdapter(store=...))
    .with_executor(SynchronousLocalTaskExecutor())    # or RayExecutor(...)
    .build()
)
result = dr.execute(final_vars=["fnl_count_by_stage"],
                    inputs={"zoho_url": "s3://..."},
                    overrides={"zoho_silver": pre_computed_df})
dr.materialize(dependencies=[...])   # fire @save_to nodes

Inspection / lineage: dr.visualize_execution(...) renders SVG of just the part that ran; dr.display_all_functions(path) renders the whole module DAG; dr.what_is_upstream_of("fnl_count_by_stage") walks ancestors.

§4The lifecycle hook system — insight-kit's seam

Adapters implement one or more of the hook interfaces in hamilton/lifecycle/base.py. Multiple adapters stack; they all fire at each stage.

pre_do_anything() — before Builder is consumed
post_graph_construct(g, modules, config) — DAG just built, before execute
pre_graph_execute(run_id, g, final_vars, inputs, overrides) — open run, start clock
pre_node_execute(run_id, node_, kwargs, task_id) — node about to run
  // node executes here (sync or remote)
post_node_execute(run_id, node_, kwargs, success, error, result, task_id) — node done
  // → read node_.tags → Run.emit_metric() / Run.claim()
post_graph_execute(run_id, g, success, error, results) — close run, write manifest
The crucial hook
post_node_execute is where InsightKitHook already wires in (src/insight_kit/hamilton/adapter.py:67). The hook receives node_.tags, the materialised result, success/error — everything needed to file OutputRecord, emit a typed claim, attach lineage. Failures fire a critic-tier claim instead of crashing the run.

§5Caching that actually saves the dedup loop

HamiltonCacheAdapter is a lifecycle hook that stores node results in a result store (file / sqlite / redis) keyed by a fingerprint of:

  • Code hash of the function body
  • Hash of every upstream input value
  • Hash of the relevant config

When you change fnl_count_by_stage, only its descendants recompute. When you tweak critic thresholds, only the critic subdag recomputes. The dedup parameter-sweep loop (4 sequential runs in dockblocks-ops) collapses to one parameterised node with 4 cached entries — change a threshold, only the diff fires.

§8Hamilton's analyst-iteration story

This is the part that matches insight-kit's "5 exploratory .py + 1 final annotated module" pattern almost word-for-word. The canonical Hamilton flow:

  1. Sketch functions in a .py file. No decorators yet.
  2. Open a notebook, import the module, dr.execute(["my_node"], inputs=...) to debug.
  3. Iterate. Add @tag for emit-mode + claim_tier.
  4. Add @check_output when the shape stabilises.
  5. Add @save_to.parquet when the output is canonical.
  6. Promote: same module, same code, now runs via ik run analyses.brevo_attribution.

There is no migration boundary between "exploration" and "production" — only progressively more decorators. That is the structural fit with insight-kit.

The right frame
Hamilton = compute orchestrator. insight-kit = analytical-claim governance layer. They compose. The hook seam is intentional in Hamilton's design — they explicitly built lifecycle adapters so other systems (MLflow, OpenLineage, custom provenance) could ride along. insight-kit is exactly that kind of ride-along.

Glossary · this page

Click any dotted term above to jump here.
Hamilton
Apache Hamilton — a micro-framework that turns a Python module's functions into a typed DAG by matching parameter names to function names. No explicit edge declarations; the module is the graph.
node
A single Python function in a Hamilton module. Its name is its identity; its typed parameters declare upstream dependencies. Hamilton resolves the graph by name-matching across all loaded modules.
FunctionGraph
Hamilton's internal DAG representation built from a set of modules. Edges are derived from parameter-name-to-function-name matches. Inspectable via dr.display_all_functions().
Driver
The top-level Hamilton object that owns the FunctionGraph, config, adapters, and executor. Created via driver.Builder(). Entry point for .execute(), .materialize(), and lineage queries.
Builder
Fluent API for constructing a Driver. Chains .with_modules(), .with_config(), .with_adapters(), .with_executor() before calling .build().
@tag
Decorator that attaches arbitrary key-value metadata to a node (e.g. owner, source, claim_tier). Tags are readable inside lifecycle hooks — this is how InsightKitHook decides what to emit.
@parameterize
Expands one function into N named nodes by sweeping a parameter dictionary. The council-of-critics pattern maps naturally: one function template, N critic configurations, each becomes its own node.
@parameterize_sources
Fan-in variant: the same function body is called with N different upstream node names as input, producing N output nodes — one per upstream source.
@extract_columns
Splits a multi-column DataFrame return into individual named nodes, one per column. Useful when a single query returns a bundle of metrics that downstream nodes consume independently.
@subdag
Embeds a reusable sub-graph inside the parent graph. The critic-of-claim pattern uses this: a sub-graph checks each derived claim, and the result node surfaces the verdict.
@parameterized_subdag
Sweeps @subdag over multiple configurations — multiple critics × multiple claim angles, all in one declaration. Generates a grid of sub-graph instantiations.
@pipe
Chains function transforms in Unix-pipe style (@pipe_input, @pipe_output). Useful for expressing sequential cleaning or normalisation steps without naming every intermediate.
@config.when
Conditionally includes or excludes a node based on Driver config keys (e.g. env="local"). Enables notebook vs. production toggling without branching logic in function bodies.
@save_to.parquet
Attaches a materializer node that persists the upstream result to parquet. Path, partitioning, and compression are configurable. Triggered via dr.materialize().
@load_from.parquet
Attaches a node that loads data from parquet as the starting point for a sub-graph, short-circuiting upstream recompute when the file already exists.
@datasaver / DataSaver
Extension point for custom I/O formats. Subclass DataSaver and register it; Hamilton then exposes @save_to.<your-format> as a decorator for any node.
materializer
Any node decorated with @save_to.* or @load_from.*. Materializers are opt-in; they run only when explicitly requested via dr.materialize(dependencies=[...]).
@check_output
Attaches validators to a node's return value. Built-ins cover type, range, pandera schema. importance="error" raises on failure; "warning" logs and continues. Basis for Hamilton's data-quality layer.
@cache
Per-node caching override. Behaviors: DEFAULT (use cache if fingerprint matches), RECOMPUTE (always rerun), DISABLE (skip caching entirely), IGNORE (run but don't store result).
lifecycle hook / NodeExecutionHook
Adapter interface in hamilton/lifecycle/base.py. Implements one or more of: pre_graph_execute, pre_node_execute, post_node_execute, post_graph_execute. Multiple adapters stack and all fire at each stage.
pre_graph_execute
Hook fired once before any nodes run. Receives run_id, the graph, final_vars, inputs, and overrides. insight-kit uses this to open a Run and start the wall clock.
pre_node_execute
Hook fired immediately before each node function is called. Receives run_id, the node object (with tags), kwargs, and optional task_id for async executors.
post_node_execute
The primary insight-kit seam. Fires after each node, with node_.tags, the materialised result, and success/error state. InsightKitHook reads tags here to dispatch OutputRecord, emit claims, and attach lineage.
post_graph_execute
Hook fired once after all nodes complete (or on graph-level failure). insight-kit closes the Run here and writes manifest.json with checksums, git SHA, and env lock.
executor
The compute backend attached to the Driver. Options: SynchronousLocalTaskExecutor (default), MultiProcessingExecutor, RayExecutor, DaskExecutor, SparkExecutor. The user's module is unchanged across executors.
fingerprint
A composite hash of (function code body + upstream input values + relevant config) used as the cache key by HamiltonCacheAdapter. A change in any constituent invalidates the node and all descendants.
HamiltonCacheAdapter
A lifecycle adapter that implements result-store caching keyed by fingerprint. Plugs into Builder.with_adapters(). Backed by file, SQLite, or Redis depending on the store configured.
what_is_upstream_of
dr.what_is_upstream_of(node_name) — returns the full ancestor set of a node. Its counterpart dr.what_is_downstream_of() returns dependents. Both are used for lineage queries and targeted recompute scoping.
final_vars
The list of node names passed to dr.execute(final_vars=[...]). Hamilton computes only the subgraph needed to produce these outputs, pruning unreachable nodes automatically.
GraphValidator / NodeValidator
GraphValidator runs structural checks across the whole DAG (e.g. no cycles, tag completeness). NodeValidator checks individual nodes. insight-kit uses these for cross-run referential integrity and Layer A/B/C namespace enforcement.
h_pandas
Hamilton plugin providing a pandas ResultBuilder. Lets dr.execute() return a single DataFrame stitched from multiple leaf node outputs, instead of a raw dict.
h_polars
Hamilton plugin for Polars eager and lazy DataFrames. Zero conversion penalty if the viz layer is polars-first; node outputs stay as Polars frames throughout the graph.
h_ray
Hamilton plugin providing RayExecutor. Distributes node execution across a Ray cluster. Useful for GPU pools or compute that outgrows a single box. Module code unchanged.
h_dask
Hamilton plugin providing DaskExecutor. Runs nodes as Dask delayed tasks, enabling distributed DataFrame operations. Best for lake-scale ETL where data exceeds local RAM.
h_spark
Hamilton plugin for Apache Spark execution. Maps Hamilton nodes to Spark transformations. Relevant only when a single Run's compute requires cluster-scale parallelism.
h_openlineage
Plugin that emits OpenLineage events from Hamilton lifecycle hooks. Useful once a real catalog (Marquez, OpenMetadata) is deployed; overkill for local-first analyst loops.
h_mlflow
Plugin for MLflow experiment tracking. Redundant for insight-kit: the manifest + claims layer already covers run metadata, parameters, and metrics with stronger provenance semantics.
h_diskcache
Plugin providing a disk-backed result store for HamiltonCacheAdapter. Simplest option for local-first analyst iteration — no Redis or database required.
h_mcp
Plugin that exposes a Hamilton DAG as an MCP (Model Context Protocol) tool server. Enables Claude Code agent loops to invoke Hamilton nodes directly as tool calls over insight-kit.
